### 🧠 Что это вообще такое?

**Уровень изоляции транзакций** — это правила, которые определяют, насколько одна транзакция "видит" изменения, сделанные другой параллельной транзакцией.

Представьте, что вы работаете в общем офисе (база данных), где несколько сотрудников (транзакций) одновременно работают с общими документами (строками таблиц). Уровень изоляции — это **политика компании**, которая определяет:
- Можно ли смотреть на черновик коллеги, пока он его еще не сдал в архив (не сделал COMMIT)?
- Можно ли видеть, как коллега исправляет цифры в отчете прямо у вас на глазах?
- Можно ли случайно дважды прочитать один и тот же документ, но увидеть в нем разные цифры?

Чем строже уровень изоляции — тем меньше "глюков" (аномалий) вы увидите, но тем медленнее будет работать система (больше блокировок, больше ожиданий). Чем слабее уровень — тем быстрее, но есть риск увидеть странные данные.

### 🔥 Какие бывают аномалии (проблемы параллельного доступа)?

Чтобы понимать уровни, нужно знать, от чего они защищают. Есть 3 основные проблемы:

| Проблема | Описание | Пример |
| :--- | :--- | :--- |
| **Dirty Read** (Грязное чтение) | Чтение данных, которые еще не закоммичены (могут откатиться). | Транзакция А изменила зарплату с 100 на 1000, но еще не сохранила. Транзакция Б читает зарплату и видит 1000. Если А сделает ROLLBACK, то Б увидела "фантомные" данные, которых никогда не существовало. |
| **Non-Repeatable Read** (Неповторяемое чтение) | В рамках одной транзакции одно и то же поле при повторном чтении дает разные значения. | Транзакция А читает зарплату → 100. Транзакция Б меняет зарплату на 200 и коммитит. Транзакция А читает зарплату снова → 200. Для А цифры изменились в процессе работы. |
| **Phantom Read** (Фантомное чтение) | При повторном чтении появляются или исчезают новые строки (не просто поля). | Транзакция А читает всех сотрудников отдела → 5 человек. Транзакция Б добавляет нового сотрудника и коммитит. Транзакция А читает снова → 6 человек. Появился "фантом". |

### 📊 Таблица уровней изоляции (по возрастанию строгости)

В SQL определено 4 стандартных уровня. Столбцы показывают, от каких проблем защищает конкретный уровень:

| Уровень изоляции | Защита от Dirty Read | Защита от Non-Repeatable Read | Защита от Phantom Read |
| :--- | :--- | :--- | :--- |
| **READ UNCOMMITTED** | ❌ Нет | ❌ Нет | ❌ Нет |
| **READ COMMITTED** | ✅ Да | ❌ Нет | ❌ Нет |
| **REPEATABLE READ** | ✅ Да | ✅ Да | ❌ Нет (кроме MySQL) |
| **SERIALIZABLE** | ✅ Да | ✅ Да | ✅ Да |

---

### 🔍 Что каждый уровень означает на практике?

1.  **READ UNCOMMITTED** (Самая слабая, супербыстрая)
    - Можно читать даже незакоммиченные данные. Почти никогда не используется в продакшене, кроме случаев, когда точность не важна (грубая статистика). Очень опасно.

2.  **READ COMMITTED** (Самый популярный)
    - Можно читать **только закоммиченные** данные. Грязных чтений нет.
    - Но если другой пользователь изменит строку и закоммитит — вы увидите новое значение при повторном чтении (Non-Repeatable Read).
    - **Это стандарт по умолчанию в PostgreSQL, SQL Server, Oracle.**

3.  **REPEATABLE READ** (Стандарт для MySQL InnoDB)
    - Строки, которые вы прочитали, "закрепляются" на время транзакции. Если читаете поле 2 раза — увидите одно и то же значение, даже если кто-то коммитил изменения.
    - Но могут добавляться новые строки (Phantom Read).
    - **Это стандарт по умолчанию в MySQL.**

4.  **SERIALIZABLE** (Самый строгий, самый медленный)
    - Имитирует последовательное выполнение транзакций. База данных блокирует не только строки, но и целые диапазоны. Полная защита от всех аномалий. Используется крайне редко, когда цена ошибки выше цены производительности (финансовые операции с очень высокой точностью).

### ⚙️ Как настроить уровень в Java / Spring?

В Spring всё делается очень просто. Есть два способа:

**Способ 1: Через аннотацию `@Transactional` (самый популярный)**

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public void updateUserData(User user) {
    // Ваш код с БД
}
```

**Важно:** Чтобы это работало, нужно, чтобы Spring управлял транзакциями (была включена аннотация `@EnableTransactionManagement` или `@Configuration`).

**Способ 2: Через настройку соединения в Hibernate**

В файле `application.properties` (Spring Boot):
```properties
spring.datasource.hikari.transaction-isolation=TRANSACTION_READ_COMMITTED
```

Или в `hibernate.properties`:
```properties
hibernate.connection.isolation=2
```
Где цифры — это уровень изоляции (подробнее в таблице ниже).

### 🧐 Какие уровни по умолчанию в популярных СУБД?

| База данных | Уровень по умолчанию | Аномалия, которая всё же возможна |
| :--- | :--- | :--- |
| **PostgreSQL** | READ COMMITTED | Non-Repeatable Read |
| **MySQL (InnoDB)** | REPEATABLE READ | Phantom Read (не всегда, есть защита) |
| **Oracle** | READ COMMITTED | Non-Repeatable Read |
| **SQL Server** | READ COMMITTED | Non-Repeatable Read |

Обратите внимание, что у **MySQL** по умолчанию стоит `REPEATABLE READ`, в отличие от всех остальных. Это связано с исторической архитектурой InnoDB и создает ряд особенностей (например, возможность "Gap Locks" — блокировок промежутков).

---

### 💎 Итог

1.  **READ COMMITTED** — золотой стандарт для 90% приложений (PostgreSQL, Oracle).
2.  **REPEATABLE READ** — используется в MySQL по умолчанию.
3.  Уровень изоляции — это **компромисс между точностью данных и производительностью**. Чем он выше, тем больше блокировок и медленнее работа.
4.  В Spring вы управляете этим через `@Transactional(isolation = ...)` или глобальные настройки подключения к БД.
