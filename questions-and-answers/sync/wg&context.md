# Внутреннее устройство `sync.WaitGroup` и `context`

## `sync.WaitGroup`

### Структура

`WaitGroup` — это **счётный семафор**. Вся его суть умещается в одной атомарной переменной:

```go
type WaitGroup struct {
    noCopy noCopy
    state  atomic.Uint64
    sema   uint32
}
```

В `state` упакованы три значения (от старших бит к младшим):

| Биты | Назначение |
|---|---|
| `[33:64]` | **counter** — сколько задач ещё не завершено |
| `[32]` | флаг «bubble» (связь с `testing/synctest`) |
| `[0:32]` | **wait count** — сколько горутин заблокировано в `Wait()` |

`noCopy` — техническая заглушка, чтобы `go vet` ругался на копирование `WaitGroup` после первого использования .

### Как работает `Add`

```go
func (wg *WaitGroup) Add(delta int) {
    state := wg.state.Add(uint64(delta) << 32)
    v := int32(state >> 32)   // counter
    w := uint32(state & 0x7fffffff)  // waiters
    // ...
}
```

Ключевая идея: `Add` делает **одну** атомарную операцию над 64-битным числом, где счётчик сдвинут на 32 бита влево. Это позволяет обновлять counter и waiters без блокировок .

Логика дальше:
- Если `v < 0` — паника (`negative WaitGroup counter`).
- Если `v > 0` — просто выходим, задачи ещё есть.
- Если `v == 0` и `w > 0` — **все задачи завершены**, надо разбудить ожидающих: вызывается `runtime_Semrelease` для каждого `waiter` .

### Как работает `Wait`

```go
func (wg *WaitGroup) Wait() {
    // ...
    if v == 0 {
        return  // все уже завершено — не блокируемся
    }
    // регистрируем себя как waiter и паркуемся на sema
    runtime_Semacquire(&wg.sema)
}
```

`Wait` сначала проверяет counter. Если он уже ноль — немедленный выход. Иначе атомарно инкрементирует `wait count` и засыпает на семафоре `sema`. Когда последний `Done` обнулит counter, он разбудит всех спящих через `Semrelease` .

### Почему 12 байт `state1` в старых версиях

В Go до появления `atomic.Uint64` структура выглядела так:

```go
state1 [3]uint32
```

Три 32-битных слова: counter, waiters, sema. Функция `state()` проверяла выравнивание: на 32-битных платформах 64-битные атомарные операции требуют выравнивания на 8 байт, но компилятор гарантировал только 4. Поэтому `state1` динамически «переставлялся»: если начало массива не выровнено на 8, то 64-битное состояние бралось из `state1[1..2]`, а `sema` — из `state1[0]` .

## `context`

### Философия

`context` — это **иммутабельное дерево**. Каждый вызов `WithCancel`/`WithValue`/`WithDeadline` не изменяет родителя, а создаёт новый узел, который хранит ссылку на родителя. Отмена (или deadline) родителя автоматически отменяет всех потомков .

Корень дерева — `emptyCtx`, возвращаемый `context.Background()` или `context.TODO()`. Это не `struct{}`, а `int`, чтобы два разных экземпляра имели **разные адреса** в памяти (нулевые структуры могут делить один адрес) .

### Основные типы

| Тип | Назначение |
|---|---|
| `cancelCtx` | Отмена через `CancelFunc` |
| `timerCtx` | Обёртка над `cancelCtx` + таймер для deadline/timeout |
| `valueCtx` | Хранение пар key-value |

### Как работает отмена (`cancelCtx`)

```go
type cancelCtx struct {
    Context
    mu       sync.Mutex
    done     atomic.Value          // chan struct{}
    children map[canceler]struct{} // дети, которых надо отменить
    err      atomic.Value
    cause    error
}
```

**`Done()`** — лениво создаёт канал. Если `Done()` никогда не вызывали, канал не аллоцируется. Это оптимизация: контекст без ожидающих не тратит память на канал .

**`cancel()`** — делает три вещи:
1. Закрывает `c.done` (все, кто ждал в `select`, просыпаются).
2. Рекурсивно вызывает `cancel()` у всех детей из `children`.
3. Если `removeFromParent == true`, удаляет себя из `children` родителя.

Важная деталь: `cancel()` идемпотентен. Повторный вызов после первого ничего не делает .

### Как работает `propagateCancel`

При создании `WithCancel(parent)` вызывается `propagateCancel(parent, child)`. Задача — «подписать» ребёнка на отмену родителя.

```go
func propagateCancel(parent Context, child canceler) {
    done := parent.Done()
    if done == nil {
        return // родитель никогда не отменяется
    }
    // Если родитель — cancelCtx, добавляем child в parent.children
    if p, ok := parentCancelCtx(parent); ok {
        p.mu.Lock()
        p.children[child] = struct{}{}
        p.mu.Unlock()
    } else {
        // Иначе запускаем горутину, которая ждёт done родителя
        go func() {
            select {
            case <-done:
                child.cancel(false, parent.Err(), Cause(parent))
            case <-child.Done():
            }
        }()
    }
}
```

Здесь два пути:
- **Родитель — `cancelCtx`**: просто добавляем ребёнка в `children`. Отмена каскадом.
- **Родитель — «чужой» Context** (не из стандартной реализации): запускается **горутина-наблюдатель**, которая ждёт `parent.Done()` и отменяет ребёнка. Именно поэтому важно вызывать `cancel()` после завершения работы: иначе горутина-наблюдатель и запись в `children` останутся в памяти .

### `timerCtx` и deadline

`WithDeadline` создаёт `timerCtx`, который встраивает `cancelCtx` и добавляет `time.Timer`. Когда таймер срабатывает, вызывается `cancel()` с ошибкой `DeadlineExceeded`. `WithTimeout` — это просто `WithDeadline(parent, time.Now().Add(timeout))` .

### `valueCtx` — связанный список

`WithValue` не использует мапу. Он создаёт узел:

```go
type valueCtx struct {
    Context
    key, val any
}
```

Поиск `Value(key)` идёт **вверх по цепочке** родителей, пока не найдёт совпадение. Это O(n) по глубине дерева. Именно поэтому не рекомендуется хранить в context много значений или использовать его для передачи параметров .

## Сравнение

| | `WaitGroup` | `context` |
|---|---|---|
| **Модель** | Счётчик + семафор | Дерево иммутабельных узлов |
| **Основная операция** | `Add`/`Done` меняют counter | `cancel` закрывает канал и каскадит вниз |
| **Синхронизация** | Атомики + `runtime_Semacquire` | Мьютекс (на `cancelCtx`) + атомики для `done`/`err` |
| **Направление сигнала** | От детей к родителю (`Done` → `Wait`) | От родителя к детям (каскадная отмена) |
| **Что даёт** | «Дождись завершения всех» | «Отмени всё, если родитель отменён» |

Если `WaitGroup` — это **точка сбора** (все пришли, можно идти), то `context` — это **дерево отмены** (родитель сказал «стоп», все ветки останавливаются). Они решают разные задачи и часто используются вместе: `WaitGroup` ждёт, пока горутины завершатся, а `context` говорит им, что пора завершаться.
