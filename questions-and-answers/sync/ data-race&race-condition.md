# Data Race vs Race Condition в Go

Это два разных понятия, которые часто путают. Важно понимать разницу, потому что data race — это конкретная техническая проблема, а race condition — более широкое понятие.

## Data Race (гонка данных)

**Определение:** Это ситуация, когда две или более горутины обращаются к одной и той же ячейке памяти **одновременно**, причём **хотя бы одна из них выполняет запись**, и при этом **отсутствует синхронизация**.

Это строго формальное определение из [Go Memory Model](https://go.dev/ref/mem).

### Пример data race

```go
var counter int

func main() {
    for i := 0; i < 1000; i++ {
        go func() {
            counter++ // DATA RACE: read + write без синхронизации
        }()
    }
    time.Sleep(time.Second)
    fmt.Println(counter) // почти всегда < 1000
}
```

Здесь `counter++` — это на самом деле три операции: чтение, инкремент, запись. Две горутины могут прочитать одно значение, обе увеличить его на 1 и записать обратно — одно приращение потеряется.

### Как обнаружить

Go имеет встроенный детектор:

```bash
go run -race main.go
go test -race ./...
```

Он выдаст подробный отчёт: какие горутины, к какой переменной, в каких строках.

### Как исправить

```go
// Вариант 1: мьютекс
var (
    mu      sync.Mutex
    counter int
)

go func() {
    mu.Lock()
    counter++
    mu.Unlock()
}()

// Вариант 2: atomic
var counter int64

go func() {
    atomic.AddInt64(&counter, 1)
}()

// Вариант 3: канал (передача владения)
ch := make(chan int, 1)
ch <- 0
go func() {
    v := <-ch
    ch <- v + 1
}()
```

## Race Condition (состояние гонки)

**Определение:** Более широкое понятие — логика программы зависит от **порядка или времени** выполнения операций, и при неблагоприятном стечении обстоятельств программа работает неправильно.

Race condition **может существовать без data race** и наоборот.

### Пример race condition БЕЗ data race

Классический пример — check-then-act с корректной синхронизацией по отдельности:

```go
type Bank struct {
    mu      sync.Mutex
    balance int
}

func (b *Bank) Withdraw(amount int) bool {
    b.mu.Lock()
    ok := b.balance >= amount  // проверка
    b.mu.Unlock()
    
    // ... какая-то работа ...
    
    b.mu.Lock()
    if ok {
        b.balance -= amount    // действие
    }
    b.mu.Unlock()
    return ok
}
```

Здесь **нет data race** (все обращения под мьютексом), но есть **race condition**: между проверкой и списанием баланс мог измениться. Классический TOCTOU (Time-of-check to time-of-use).

### Пример race condition на каналах

```go
func main() {
    ch := make(chan int)
    
    go func() { ch <- 1 }()
    go func() { ch <- 2 }()
    
    // Какое значение придёт первым — недетерминировано.
    // Если логика зависит от этого порядка — это race condition.
    fmt.Println(<-ch)
}
```

Формально это не data race (каналы синхронизируют), но поведение зависит от планировщика.

### Пример "безобидного" data race, который не является race condition

```go
var flag int32

go func() { atomic.StoreInt32(&flag, 1) }()
go func() { _ = atomic.LoadInt32(&flag) }()
```

Хотя это атомарные операции, формально в терминах C/C++ memory model это не data race — но если логика зависит от того, увидим ли мы `1` или `0`, это может быть race condition.

Обратный случай: несинхронизированное чтение переменной-флага для логирования (результат не важен) — формально это **data race** (детектор сработает), но **не race condition** с точки зрения логики.

## Сводная таблица

| Критерий | Data Race | Race Condition |
|---|---|---|
| Природа | Техническая (модель памяти) | Логическая (семантика программы) |
| Определение | Одновременный доступ к памяти, ≥1 запись, без синхронизации | Результат зависит от порядка/времени выполнения |
| Детектируется `-race` | Да | Нет (обычно) |
| Может быть без второго | Да | Да |
| Последствия | Неопределённое поведение, порча данных, краши | Некорректная бизнес-логика |
| Инструменты | `go test -race`, `-race` | Ревью кода, тесты, моделирование |

---

## Ключевые выводы

1. **Data race ⊂ Race condition** не выполняется ни в одну сторону — это пересекающиеся множества.

2. **Data race всегда плох** в Go — это UB по определению memory model. Даже если "сейчас работает", компилятор и планировщик могут сломать код.

3. **Race condition опаснее** — его не поймает `-race`, потому что формально синхронизация есть, но логика неверна. Ловится только ревью и тестами.

4. **Устранение data race ≠ устранение race condition.** Мьютекс убирает data race, но если критическая секция захватывает не всю логическую операцию — race condition останется.

5. В Go идиоматично: *"Don't communicate by sharing memory; share memory by communicating"* — каналы помогают бороться с обоими типами проблем, если правильно моделировать владение данными.
