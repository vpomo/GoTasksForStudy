**В REST когда надо использовать PUT, а когда PATCH?**
Отличный вопрос! Это классика REST-собеседований, и здесь часто возникает путаница даже у опытных разработчиков. Давай разберем принципиальные различия.

---

## PUT vs PATCH: Идемпотентность и семантика

### 1. PUT — Замена ресурса целиком

**PUT** используется для **полной замены** ресурса по указанному URL. Ты отправляешь *полное* представление ресурса, и сервер заменяет существующий ресурс этим новым состоянием.

**Ключевые характеристики:**
- **Идемпотентность:** PUT строго идемпотентен. Вызов 1 раз или 10 раз подряд с одним телом приводит к одинаковому результату.
- **Полная замена:** Отсутствующие поля обычно интерпретируются как `null` или значения по умолчанию (сбрасываются).
- **URL идентифицирует конкретный ресурс:** `PUT /users/123` означает "заменить пользователя 123".

```http
// До: пользователь 123
{
    "name": "John",
    "email": "john@old.com",
    "age": 30
}

// PUT /users/123
{
    "name": "John Updated",
    "email": "john@new.com"
    // age отсутствует — обычно станет null или 0
}

// После: пользователь 123 полностью заменен
{
    "name": "John Updated",
    "email": "john@new.com",
    "age": 0  // или null — потеряли данные!
}
```

---

### 2. PATCH — Частичное обновление

**PATCH** используется для **частичного обновления** ресурса. Ты отправляешь *набор изменений* (инструкции, а не полное состояние), которые сервер применяет к ресурсу.

**Ключевые характеристики:**
- **Не гарантированно идемпотентен:** Может быть идемпотентным, если реализован правильно, но стандарт не требует этого.
- **Частичное изменение:** Обновляются только указанные поля, остальные сохраняются.
- **Формат тела:** Обычно JSON, но может быть JSON Patch (RFC 6902) или Merge Patch (RFC 7396).

```http
// До: пользователь 123
{
    "name": "John",
    "email": "john@old.com",
    "age": 30
}

// PATCH /users/123 (Merge Patch)
{
    "email": "john@new.com"
    // age не указан — остается 30
}

// После: обновлен только email
{
    "name": "John",
    "email": "john@new.com",
    "age": 30
}
```

---

### 3. Ключевые различия

| Характеристика | PUT | PATCH |
|----------------|-----|-------|
| **Семантика** | Полная замена ресурса | Частичное обновление |
| **Идемпотентность** | Да (строго) | Не гарантирована (но обычно реализуют идемпотентно) |
| **Тело запроса** | Полное состояние ресурса | Набор изменений (diff) |
| **Что с отсутствующими полями** | Сбрасываются в дефолт/null | Остаются без изменений |
| **Content-Type** | `application/json` (или др.) | `application/merge-patch+json` или `application/json-patch+json` |
| **Когда использовать** | Полная замена, upload файлов, идемпотентные операции | Частичные обновления, изменение нескольких полей |

---

### 4. Практические примеры

#### Когда использовать PUT:

**А. Полная замена ресурса**
```http
PUT /users/123
Content-Type: application/json

{
    "name": "Jane Smith",
    "email": "jane@example.com",
    "age": 28,
    "role": "admin"
}
```

**Б. Создание ресурса с известным ID (идиоматично)**
```http
PUT /users/123  # создает пользователя 123, если не существует
```

**В. Загрузка файлов**
```http
PUT /documents/report.pdf
Content-Type: application/pdf

<бинарные данные>
```

#### Когда использовать PATCH:

**А. Обновление нескольких полей без сброса остальных**
```http
PATCH /users/123
Content-Type: application/merge-patch+json

{
    "email": "newemail@example.com",
    "lastLogin": "2026-03-23T10:00:00Z"
}
```

**Б. Операции с массивами (JSON Patch)**
```http
PATCH /users/123
Content-Type: application/json-patch+json

[
    { "op": "replace", "path": "/email", "value": "new@example.com" },
    { "op": "add", "path": "/tags/-", "value": "premium" },
    { "op": "remove", "path": "/oldField" }
]
```

**В. Когда клиент не знает полное состояние ресурса**
Например, мобильное приложение, которое обновляет только те поля, которые пользователь изменил.

---

### 5. Подводные камни и нюансы

#### А. PUT не для частичного обновления!
Частая ошибка — использовать PUT с частичным телом, ожидая, что остальные поля сохранятся. Это нарушает семантику HTTP и приводит к потере данных.

```go
// ПЛОХО! PUT должен заменять целиком
// Клиент отправил только name, но age сбросится
func UpdateUserPUT(w http.ResponseWriter, r *http.Request) {
    var updates User
    json.NewDecoder(r.Body).Decode(&updates)
    
    // Если updates содержит только name — age станет 0!
    user := db.GetUser(id)
    user.Name = updates.Name  // age теряется
    user.Email = updates.Email // если пусто — потеряли email
    db.Save(user)
}

// ХОРОШО: PUT заменяет полностью
func UpdateUserPUT(w http.ResponseWriter, r *http.Request) {
    var newUser User
    json.NewDecoder(r.Body).Decode(&newUser)
    
    // Полностью заменяем существующего пользователя
    db.ReplaceUser(id, newUser)
}
```

#### Б. Идемпотентность PATCH

Хотя PATCH не обязан быть идемпотентным, хороший API делает его таковым:

```http
// НЕ идемпотентно (плохо):
PATCH /counter
{ "op": "increment" }  // каждый вызов увеличивает счетчик

// Идемпотентно (хорошо):
PATCH /counter
{ "value": 42 }  // всегда устанавливает в 42
```

#### В. Content-Type важен!

Для PATCH нужно явно указывать тип:
- `application/merge-patch+json` — простое слияние полей
- `application/json-patch+json` — полный набор операций (RFC 6902)

Многие разработчики ошибочно используют `application/json`, что технически допустимо, но не следует стандартам.

---

### 6. Когда PUT, когда PATCH — принятие решения

```
Нужно обновить ресурс?
│
├─ Клиент знает ПОЛНОЕ состояние ресурса?
│  └─ ДА → PUT (замена целиком)
│
├─ Нужно обновить ТОЛЬКО несколько полей?
│  └─ ДА → PATCH
│
├─ Операция сложная (добавление в массив, вложенные изменения)?
│  └─ ДА → PATCH с JSON Patch
│
└─ Операция НЕ идемпотентна (например, инкремент счетчика)?
   └─ Используй POST (не PUT и не PATCH)
```

---

### 7. Резюме для собеседования

**Короткий ответ:**
> PUT используется для полной замены ресурса, должен быть идемпотентным. PATCH — для частичного обновления, позволяет изменять отдельные поля без влияния на остальные. PUT требует передачи полного состояния, PATCH — только изменений. Выбор зависит от того, знает ли клиент полное состояние ресурса и хочет ли он сбросить неуказанные поля.

**Сеньор-уровень добавление:**
> Важно также учитывать, что не все клиенты поддерживают PATCH (например, некоторые старые прокси или кэши), поэтому иногда PUT с полным состоянием — это более консервативный, надежный выбор. Для сложных API я предпочитаю использовать PATCH с JSON Patch (RFC 6902), так как он дает четкую спецификацию операций и работает предсказуемо с массивами и вложенными структурами.

## Полная классификация HTTP методов в REST

### 1. Сравнительная таблица всех методов

| Метод | Семантика | Безопасный¹ | Идемпотентный² | Тело запроса | Тело ответа | Типичные статусы |
|-------|-----------|-------------|----------------|--------------|-------------|------------------|
| **GET** | Получение ресурса | ✅ Да | ✅ Да | ❌ Нет | Ресурс | 200, 404, 400, 301, 304 |
| **HEAD** | Получение только заголовков | ✅ Да | ✅ Да | ❌ Нет | ❌ Нет | 200, 404, 301 |
| **OPTIONS** | Получение доступных методов | ✅ Да | ✅ Да | ❌ Нет | Список методов | 200, 204, 403 |
| **POST** | Создание / выполнение операции | ❌ Нет | ❌ Нет | ✅ Да | Созданный ресурс или статус | 201, 202, 200, 400, 409, 422 |
| **PUT** | Полная замена / создание с ID | ❌ Нет | ✅ Да | ✅ Да | Обновленный ресурс или статус | 200, 201, 204, 400, 409 |
| **PATCH** | Частичное обновление | ❌ Нет | ⚠️ Частично³ | ✅ Да | Обновленный ресурс или статус | 200, 204, 400, 409, 422 |
| **DELETE** | Удаление ресурса | ❌ Нет | ✅ Да | ❌ Нет (редко) | Статус (часто пустое) | 204, 200, 202, 404, 409 |
| **TRACE** | Диагностика (echo запроса) | ✅ Да | ✅ Да | ❌ Нет | Полученный запрос | 200, 405 |
| **CONNECT** | Туннель (прокси) | ❌ Нет | ❌ Нет | ✅ Да | Нет (устанавливает туннель) | 200 |

---

**Примечания:**
1. **Безопасный (Safe)** — не изменяет состояние сервера. Можно кэшировать, предзагружать.
2. **Идемпотентный (Idempotent)** — многократное выполнение дает тот же результат, что и однократное.
3. **PATCH** не гарантирует идемпотентность по спецификации, но на практике его часто реализуют идемпотентным.

## 2. Детальный разбор методов и статусов

### GET — Получение ресурсов

**Назначение:** Чтение данных без побочных эффектов.

**Типичные статусы:**
| Статус | Ситуация |
|--------|----------|
| **200 OK** | Успешное получение ресурса(ов) |
| **404 Not Found** | Ресурс не найден |
| **400 Bad Request** | Некорректные параметры запроса |
| **301 Moved Permanently** | Ресурс перемещен на новый URL |
| **304 Not Modified** | Кэш актуален (If-None-Match / If-Modified-Since) |
| **206 Partial Content** | Частичное получение (Range header) |

```http
GET /users/123 HTTP/1.1
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{
    "id": 123,
    "name": "John Doe",
    "email": "john@example.com"
}
```

---

### POST — Создание ресурса или выполнение операции

**Назначение:** Создание нового ресурса (сервер генерирует ID) или выполнение неидемпотентных операций.

**Типичные статусы:**
| Статус | Ситуация |
|--------|----------|
| **201 Created** | Ресурс успешно создан. Location header содержит URL нового ресурса |
| **200 OK** | Операция выполнена, возвращает результат (не всегда создание) |
| **202 Accepted** | Запрос принят в обработку (асинхронная операция) |
| **400 Bad Request** | Ошибка валидации, неверный формат |
| **409 Conflict** | Конфликт (например, дубликат уникального поля) |
| **422 Unprocessable Entity** | Синтаксически верно, но семантически ошибочно |

```http
POST /users HTTP/1.1
Content-Type: application/json

{
    "name": "Jane Smith",
    "email": "jane@example.com"
}

HTTP/1.1 201 Created
Location: /users/456
Content-Type: application/json

{
    "id": 456,
    "name": "Jane Smith",
    "email": "jane@example.com",
    "createdAt": "2026-03-23T10:00:00Z"
}
```

---

### PUT — Полная замена / создание с известным ID

**Назначение:** Полная замена существующего ресурса или создание по конкретному URL.

**Типичные статусы:**
| Статус | Ситуация |
|--------|----------|
| **200 OK** | Ресурс успешно обновлен, возвращена новая версия |
| **201 Created** | Ресурс создан (не существовал до этого) |
| **204 No Content** | Обновление выполнено, тело ответа пустое |
| **400 Bad Request** | Неверные данные |
| **409 Conflict** | Конфликт версий (при optimistic locking) |

```http
PUT /users/123 HTTP/1.1
Content-Type: application/json

{
    "name": "John Updated",
    "email": "john@updated.com",
    "age": 31
}

HTTP/1.1 200 OK
Content-Type: application/json

{
    "id": 123,
    "name": "John Updated",
    "email": "john@updated.com",
    "age": 31,
    "updatedAt": "2026-03-23T10:30:00Z"
}
```

---

### PATCH — Частичное обновление

**Назначение:** Частичное изменение ресурса без замены всего состояния.

**Типичные статусы:**
| Статус | Ситуация |
|--------|----------|
| **200 OK** | Успешное обновление, возвращена новая версия |
| **204 No Content** | Обновление выполнено, тело пустое |
| **400 Bad Request** | Неверный формат патча |
| **409 Conflict** | Конфликт версий |
| **422 Unprocessable Entity** | Операция патча невозможна |

```http
PATCH /users/123 HTTP/1.1
Content-Type: application/merge-patch+json

{
    "email": "newemail@example.com"
}

HTTP/1.1 200 OK
Content-Type: application/json

{
    "id": 123,
    "name": "John Doe",          // осталось без изменений
    "email": "newemail@example.com", // обновлено
    "age": 30                     // осталось без изменений
}
```

---

### DELETE — Удаление ресурса

**Назначение:** Удаление указанного ресурса.

**Типичные статусы:**
| Статус | Ситуация |
|--------|----------|
| **204 No Content** | Успешно удалено, тело ответа пустое |
| **200 OK** | Удалено, возвращена информация об удалении |
| **202 Accepted** | Удаление принято в обработку (асинхронно) |
| **404 Not Found** | Ресурс не найден (уже удален или никогда не существовал) |

```http
DELETE /users/123 HTTP/1.1

HTTP/1.1 204 No Content
```

---

### HEAD — Получение метаданных

**Назначение:** Получить заголовки, которые вернул бы GET, без тела ответа. Используется для проверки существования, размера, последнего изменения.

```http
HEAD /users/123 HTTP/1.1

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 342
ETag: "abc123"
Last-Modified: Wed, 21 Oct 2026 07:28:00 GMT
```

## 3. Классификация по группам

### Коллекции vs Элементы

| Действие | URL | Метод | Статус успеха |
|----------|-----|-------|---------------|
| **Список** | `/users` | GET | 200 |
| **Создание** | `/users` | POST | 201 |
| **Получение** | `/users/{id}` | GET | 200 / 404 |
| **Полная замена** | `/users/{id}` | PUT | 200 / 201 / 204 |
| **Частичное обновление** | `/users/{id}` | PATCH | 200 / 204 |
| **Удаление** | `/users/{id}` | DELETE | 204 / 200 |

### Специализированные операции

Для действий, которые не вписываются в CRUD, используют POST:

```http
POST /users/123/activate      # активация пользователя
POST /users/123/reset-password # сброс пароля
POST /search?q=golang         # сложный поиск
POST /batch                   # batch-операции
```

## 4. Выбор статусов — практические рекомендации

### 2xx — Успех

| Код | Название | Когда использовать |
|-----|----------|-------------------|
| **200** | OK | GET, PUT, PATCH успешны, возвращают данные |
| **201** | Created | POST успешно создал ресурс |
| **202** | Accepted | Асинхронная операция принята |
| **204** | No Content | Успешно, но нет данных в ответе (DELETE, PUT без возврата) |
| **206** | Partial Content | Частичное получение (пагинация, range запросы) |

### 3xx — Редиректы

| Код | Название | Когда использовать |
|-----|----------|-------------------|
| **301** | Moved Permanently | Ресурс окончательно перемещен |
| **304** | Not Modified | Кэш актуален (условный GET) |

### 4xx — Ошибки клиента

| Код | Название | Когда использовать |
|-----|----------|-------------------|
| **400** | Bad Request | Неверный формат запроса, отсутствуют обязательные поля |
| **401** | Unauthorized | Требуется аутентификация |
| **403** | Forbidden | Аутентифицирован, но нет прав |
| **404** | Not Found | Ресурс не найден |
| **405** | Method Not Allowed | Метод не поддерживается для этого ресурса |
| **409** | Conflict | Конфликт (дубликат, версионный конфликт) |
| **415** | Unsupported Media Type | Неверный Content-Type |
| **422** | Unprocessable Entity | Валидация пройдена, но бизнес-логика не позволяет |
| **429** | Too Many Requests | Превышен лимит запросов |

### 5xx — Ошибки сервера

| Код | Название | Когда использовать |
|-----|----------|-------------------|
| **500** | Internal Server Error | Необработанная ошибка (не используй как default!) |
| **502** | Bad Gateway | Проблемы с upstream |
| **503** | Service Unavailable | Сервис временно недоступен |
| **504** | Gateway Timeout | Таймаут от upstream |

## 5. Резюме для собеседования

**Короткий ответ:**
> В REST используются стандартные HTTP методы: GET (чтение, безопасный), POST (создание/операции), PUT (полная замена), PATCH (частичное обновление), DELETE (удаление), а также вспомогательные HEAD, OPTIONS. Выбор статусов следует семантике: 200/201 для успеха, 4xx для ошибок клиента, 5xx для ошибок сервера. Важно соблюдать идемпотентность: GET, PUT, DELETE должны быть идемпотентны, POST — нет, PATCH — по возможности.

**Сеньор-уровень:**
> При проектировании API я обращаю внимание на:
> 1. **Идемпотентность** — критична для надежности при ретраях
> 2. **Консистентность статусов** — для всех ресурсов одинаковые коды в одинаковых ситуациях
> 3. **Проблема POST vs PUT** — если клиент знает ID ресурса заранее, лучше использовать PUT (идемпотентность)
> 4. **202 Accepted** для асинхронных операций с возвратом статуса через Location или заголовок `Retry-After`
> 5. **Проблема 404 vs 403** — в безопасности иногда возвращают 404 даже при наличии ресурса, чтобы не раскрывать существование
