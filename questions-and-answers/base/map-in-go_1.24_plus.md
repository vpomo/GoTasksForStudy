### Об особенностях реализации map в Go 1.24+

В Go 1.24 произошло фундаментальное изменение: стандартная реализация `map` была полностью переписана на основе **Swiss Table**, заменив старую структуру «корзины + цепочки переполнения» .

### 🧬 Почему потребовалась переработка

Старая реализация, хотя и была рабочей, имела несколько узких мест, которые становились всё более заметными с ростом нагрузки:
*   **«Погоня за указателями»**: При коллизиях старые корзины образовывали цепочку переполнения, что заставляло процессор прыгать по разным участкам памяти, ухудшая кэширование .
*   **Высокая стоимость промаха**: Поиск несуществующего ключа мог быть медленным из-за необходимости проходить всю цепочку .
*   **Тяжёлая эвакуация**: Старый механизм роста (`oldbuckets` + `nevacuate`) был сложным в реализации и поддержке .

Новая реализация на базе Swiss Table решает эти проблемы, делая упор на **кэш-дружественность** и **SIMD-подобные вычисления** .

### 🗺️ Новая структура: «каталог» и «таблицы»

Новая `map` организована как иерархия: `map` -> каталог (directory) -> таблицы (tables) -> группы (groups) -> слоты (slots) .

*   **Каталог и Extendible Hashing**: Для выбора таблицы используются старшие биты хеша ключа. Каталог — это массив указателей на таблицы, и его размер растёт по мере необходимости. Это позволяет использовать **инкрементальный рост**: вместо того чтобы перестраивать всю карту разом, можно перестраивать только одну таблицу .
*   **Группы и Слоты**: Внутри каждой таблицы данные хранятся в **группах** по 8 слотов. Именно здесь и происходит «магия» Swiss Table .

### ✨ Ключевые особенности Swiss Table в Go

1.  **Разделение метаданных и данных**: Для каждой группы выделяется **64-битное управляющее слово (Control Word)**, где каждый байт (8 байт) соответствует одному слоту. Этот байт хранит **7-битный «отпечаток» (H2)** хеша ключа или специальные маркеры состояния (пусто, удалено) .
2.  **SIMD-подобное сканирование**: Поиск ключа в группе начинается не с чтения самих ключей, а с **быстрого параллельного сравнения** байтов управляющего слова с искомым H2. Это позволяет за одну операцию отсеять почти все неподходящие слоты .
3.  **Управление удалением (Tombsones)**: При удалении элемента из полностью заполненной группы слот помечается как «могила» (tombstone, `0b11111110`), чтобы не разрывать последовательность поиска. Если в группе есть пустой слот, элемент просто помечается пустым .
4.  **Устранение цепочек переполнения**: Вместо этого используется **линейное или квадратичное пробирование** следующей группы .

### 📊 Что это даёт на практике

Согласно независимым бенчмаркам, переход на Swiss Table обеспечил значительный прирост производительности :

| Операция | Ускорение (Go 1.23 -> 1.24) |
| :--- | :--- |
| **Вставка (Insert)** | ~ **33%** |
| **Поиск (Lookup)** | ~ **29%** |
| **Удаление (Delete)** | ~ **39%** |

### ⚠️ Важные замечания

*   **Потокобезопасность не изменилась**: `map` по-прежнему **не безопасна** для конкурентного использования. Параллельная запись или одновременное чтение и запись по-прежнему приведут к фатальной ошибке .
*   **`sync.Map` тоже улучшился**: В Go 1.24 также была переработана реализация `sync.Map`, что снизило конкуренцию при изменениях, особенно для больших карт с разными наборами ключей .
*   **Итерация остаётся недетерминированной**: Порядок обхода `map` намеренно рандомизирован, и это не изменилось .

# Карта (map) в Go 1.24+: как устроена Swiss Table изнутри

## Введение: зачем переписали карту

В Go 1.24 команда Go полностью переписала реализацию встроенной карты (`map`), заменив старую структуру «корзин и цепочек переполнения» на **Swiss Table** — дизайн, вдохновлённый библиотекой Abseil от Google. Это не косметическое изменение: новая реализация быстрее, лучше использует кэш процессора и проще в поддержке.

Чтобы понять, что именно изменилось, нужно сначала разобраться, как данные лежат в памяти.

---

## Часть 1: Структура данных

### Группы (Groups) — основа всего

В Swiss Table все данные разбиты на **группы по 8 слотов** каждая. Это ключевая единица организации.

Внутри одной группы лежат три вещи:

1. **Control word** — 64-битное число (8 байт), где каждый байт соответствует одному слоту.
2. **Ключи (keys)** — 8 ключей.
3. **Значения (values)** — 8 значений.

Каждый байт в control word содержит либо **7-битный отпечаток хеша** (называемый `h2`), либо специальный маркер состояния слота.

### Как выглядит группа: конкретный пример

Представь, что у нас есть группа с 4 заполненными слотами. Вот как она может выглядеть:

```
Control Word (8 байт):  [ 23 | 89 | 50 | 47 | 80 | 80 | 80 | 80 ]
                         слот0 слот1 слот2 слот3 слот4 слот5 слот6 слот7
                         
Keys:                   [ 56 | 32 | 21 | 78 |  -  |  -  |  -  |  -  ]
                        
Values:                 [ "a"| "b"| "c"| "d"|  -  |  -  |  -  |  -  ]
```

Здесь:
- `23`, `89`, `50`, `47` — это `h2` отпечатки хешей ключей `56`, `32`, `21`, `78` соответственно.
- `80` (в двоичном виде `10000000`) — это маркер `ctrlEmpty`, означающий, что слот пуст.

### Откуда берутся h1 и h2

Когда ты вставляешь ключ, Go вычисляет его хеш. Этот хеш **разрезается на две части**:

```
Полный хеш ключа (64 бита):
┌─────────────────────────────────────┬──────────────┐
│         h1 (старшие 57 бит)         │ h2 (7 бит)   │
└─────────────────────────────────────┴──────────────┘
         ↓                                      ↓
   Выбирает группу                    Хранится в control word
   (через каталог таблиц)             (для быстрого поиска)
```

- **h1** используется для выбора, в какую **группу** идти.
- **h2** сохраняется в control word — это «подсказка» для быстрого поиска.

### Что такое «каталог» (directory) и «таблица» (table)

Карта — это не просто один массив групп. Это иерархия:

```
Map
 └── Directory (каталог)
      ├── Table 0 → [ Group, Group, Group, ... ]
      ├── Table 1 → [ Group, Group, ... ]
      └── Table 2 → [ Group, Group, ... ]
```

- **Таблица** — это набор групп. Внутри одной таблицы количество групп всегда степень двойки.
- **Каталог** — массив указателей на таблицы. Старшие биты хеша (`h1`) определяют, в какую таблицу идти.
- Изначально карта состоит из **одной таблицы**. Когда таблица достигает предельного размера, она **разделяется на две**, и появляется каталог.

## Часть 2: Как происходят операции

### Поиск (Lookup)

Допустим, мы ищем ключ `25`, и его `h2 = 89`.

**Шаг 1.** Вычисляем хеш ключа `25`. Разделяем на `h1` и `h2` (допустим, `h1` указывает на группу 0, `h2 = 89`).

**Шаг 2.** Загружаем control word группы 0 — **всего 8 байт**. Это одна операция чтения памяти.

**Шаг 3.** Сравниваем `h2 = 89` со **всеми 8 байтами control word одновременно** (SIMD-подобная операция). Получаем битовую маску, например: `[0, 1, 0, 0, 0, 0, 0, 0]` — совпадение во втором слоте.

**Шаг 4.** Только теперь читаем **ключ из второго слота** и сравниваем его с `25`. Если совпал — читаем значение.

**Почему это быстро:** мы не читаем ключи и значения из всех 8 слотов. Мы читаем только 8 байт подсказок, и только если подсказка совпала — обращаемся к ключу. В большинстве случаев подсказки не совпадают, и мы сразу идём к следующей группе.

### Вставка (Insert)

Вставка ключа `98` с `h2 = 50`:

**Шаг 1.** Вычисляем `h1` (выбор группы) и `h2 = 50`.

**Шаг 2.** Ищем в control word группы слот, который пуст или удалён (`ctrlEmpty` или `ctrlDeleted`). Это тоже одна операция сравнения по 8 байтам.

**Шаг 3.** Находим свободный слот (например, слот 3). Записываем в control word байт `50`, в keys[3] — ключ `98`, в values[3] — значение.

**Результат:**

```
Control Word:  [ 23 | 89 | 50 | 50 | 80 | 80 | 80 | 80 ]
                        ↑ слот3 получил h2=50
                        
Keys:          [ 56 | 32 | 21 | 98 |  -  |  -  |  -  |  -  ]
                              ↑ слот3 получил ключ 98
```

### Коллизии и пробирование

Если `h1` указывает на группу, где все слоты заняты, мы переходим к следующей группе. Это называется **пробированием (probing)**.

Swiss Table в Go использует **квадратичное пробирование** (quadratic probing) для уменьшения кластеризации.

### Удаление и «надгробия» (tombstones)

Удаление — это не просто «очистить слот», потому что это разорвало бы цепочку пробирования. Если ключ A был в слоте 3, а ключ B (с коллизией) пробировал до слота 6, то удаление A не должно заставлять поиск B останавливаться на слоте 3.

Поэтому:
- Если группа **не полностью заполнена**, слот помечается как `ctrlEmpty` (можно безопасно остановить поиск).
- Если группа **полностью заполнена**, слот помечается как `ctrlDeleted` (надгробие, `0b11111110`), чтобы поиск продолжался.

Надгробия очищаются во время роста (эвакуации).

## Часть 3: Эвакуация (Grow) — когда и как

### При каких условиях начинается рост

Рост запускается, когда **коэффициент заполнения (load factor)** превышает порог. В стандартной карте Go это **87.5%** (`maxAvgGroupLoad / SwissMapGroupSlots`).

Коэффициент заполнения = количество занятых слотов / общее количество слотов.

Когда таблица заполнена на 87.5%, вероятность коллизий и длина цепочек пробирования резко возрастают. Поэтому карта растёт заранее.

### Как именно происходит рост

Рост в Swiss Table Go — это **двухэтапный процесс**:

**Этап 1: Внутри одной таблицы — удвоение.**

Если таблица не достигла предела `maxTableCapacity`, она просто **удваивает количество групп**.

Пример: таблица с 4 группами (32 слота) становится таблицей с 8 группами (64 слота).

**Этап 2: Если таблица достигла предела — разделение (split).**

Когда таблица становится слишком большой, она **разделяется на две таблицы**. Каталог расширяется, и теперь старшие биты хеша (`h1`) определяют, в какую из двух таблиц идти.

Это называется **расширяемым хешированием (extendible hashing)**.

### Пошаговое описание эвакуации

Допустим, у нас есть таблица с 2 группами (16 слотов), заполненная на 87.5% (14 элементов). Нужно вставить 15-й элемент.

**Шаг 1.** Создаётся **новая таблица** с 4 группами (32 слота).

**Шаг 2.** Все элементы из старой таблицы **перераспределяются** в новую. Для каждого элемента:
- Вычисляется хеш ключа.
- Разделяется на `h1` и `h2`.
- `h1` определяет новую группу (учитывая новое количество групп).
- `h2` записывается в control word новой группы.

**Шаг 3.** Старая таблица отбрасывается. Каталог обновляется: указатель на старую таблицу заменяется указателем на новую.

**Важно:** эвакуация в Go **инкрементальная** на уровне таблиц. Карта разбита на множество таблиц, и растёт только **одна таблица** за раз. Это ограничивает худшую задержку при вставке.

### Конкретный пример эвакуации

Было (старая таблица, 1 группа, все слоты заняты):

```
Control Word:  [ 23 | 89 | 50 | 47 | 12 | 34 | 56 | 78 ]
Keys:          [ 56 | 32 | 21 | 78 | 90 | 11 | 45 | 67 ]
```

Новая таблица (2 группы). Перераспределяем по новым `h1`:

```
Группа 0 (h1 mod 2 == 0):
Control Word:  [ 23 | 50 | 12 | 56 | 80 | 80 | 80 | 80 ]
Keys:          [ 56 | 21 | 90 | 45 |  -  |  -  |  -  |  -  ]

Группа 1 (h1 mod 2 == 1):
Control Word:  [ 89 | 47 | 34 | 78 | 80 | 80 | 80 | 80 ]
Keys:          [ 32 | 78 | 11 | 67 |  -  |  -  |  -  |  -  ]
```

Элементы, которые раньше были в одной группе, теперь могут оказаться в разных группах, потому что изменилось количество групп, а значит, и то, как `h1` выбирает группу.

## Часть 4: Почему это быстрее старой карты

### Старая карта: проблема «слепого» поиска

В старой карте (до 1.24) структура корзины выглядела так:

```
[корзина]
tophash[8]  — 8 байт хешей
keys[8]     — ключи
values[8]   — значения
overflow    — указатель на следующую корзину
```

Проблема: чтобы найти ключ, процессор **читал все 8 ключей и значений** из корзины, даже если ключ был в первом слоте. Это тратило пропускную способность памяти.

### Swiss Table: сначала подсказки, потом данные

В Swiss Table:
1. Сначала читаются **только 8 байт control word**.
2. Сравниваются с `h2` **параллельно** (одна операция).
3. Только при совпадении читается **конкретный ключ**.

Это как сравнивать оглавление книги вместо чтения всех страниц.

### Отсутствие цепочек переполнения

Старая карта при переполнении корзины создавала **цепочку** из дополнительных корзин. Это означало прыжки по указателям и плохую локальность кэша.

Swiss Table использует **линейное/квадратичное пробирование** по группам в пределах одной таблицы — данные лежат последовательно.

---

## Итог

Карта в Go 1.24+ — это **Swiss Table**:

- Данные разбиты на **группы по 8 слотов**.
- Каждая группа имеет **control word** — 8 байт с `h2` отпечатками для быстрого поиска.
- Поиск читает только подсказки, а ключи — только при совпадении.
- Рост происходит при заполнении **87.5%**.
- Эвакуация **инкрементальная**: растёт одна таблица за раз, чтобы не блокировать программу надолго.
- При достижении предела таблица **разделяется**, появляется **каталог** для выбора таблицы по старшим битам хеша.

Эта архитектура даёт значительный прирост производительности и лучшую предсказуемость по сравнению со старой реализацией.
