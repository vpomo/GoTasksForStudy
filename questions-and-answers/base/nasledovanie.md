# Наследование в Go: как его эмулируют

В Go **нет наследования** в классическом смысле. Нельзя написать `class B extends A`. Вместо этого используется **встраивание (embedding)** — композиция, которая внешне напоминает наследование, но таковой не является.

Ниже — несколько примеров, которые показывают:
1. Что такое встраивание и как оно выглядит как «наследование».
2. Почему это **не** наследование (нет подтипизации, нет `super`).
3. Как эмулировать переопределение методов через интерфейсы.

---

## 1. Базовый пример: встраивание структуры

```go
package main

import "fmt"

// "Базовый класс" — на самом деле просто структура
type Animal struct {
    Name string
}

// Метод "базового класса"
func (a Animal) Speak() {
    fmt.Printf("%s издаёт звук\n", a.Name)
}

func (a Animal) Breathe() {
    fmt.Printf("%s дышит\n", a.Name)
}

// "Наследник" — структура, которая встраивает Animal
type Dog struct {
    Animal // встраивание (анонимное поле)
    Breed  string
}

// Свой метод
func (d Dog) WagTail() {
    fmt.Printf("%s виляет хвостом\n", d.Name)
}

func main() {
    d := Dog{
        Animal: Animal{Name: "Рекс"},
        Breed:  "Лабрадор",
    }

    // Методы "родителя" доступны напрямую — это называется promotion
    d.Speak()    // Рекс издаёт звук
    d.Breathe()  // Рекс дышит

    // Свой метод
    d.WagTail()  // Рекс виляет хвостом

    // Можно обратиться и явно
    d.Animal.Speak() // Рекс издаёт звук
}
```

**Что здесь похоже на наследование:**
- `Dog` получает доступ к полю `Name` и методам `Speak`, `Breathe` так, как если бы они были его собственными.

**Что здесь НЕ наследование:**
- `Dog` не является подтипом `Animal`. Нельзя написать `var a Animal = d`.
- Нет `super`. Можно только явно обратиться к `d.Animal`.
- Нет виртуальных методов: если `Dog` определит свой `Speak`, старый `Animal.Speak` не будет вызван автоматически из `Animal.Breathe`.

---

## 2. Почему это не подтипизация (ключевой момент)

Попробуем передать `Dog` туда, где ожидается `Animal`:

```go
func describe(a Animal) {
    a.Speak()
}

func main() {
    d := Dog{Animal: Animal{Name: "Рекс"}}

    describe(d) // ❌ Ошибка компиляции!
    // cannot use d (variable of type Dog) as Animal value
}
```

**В Java это сработало бы** благодаря наследованию:
```java
void describe(Animal a) { a.speak(); }
describe(new Dog()); // ✅ OK
```

**В Go — нет.** Чтобы это заработало, нужен интерфейс (см. следующий пример).

## 3. Эмуляция «переопределения» через интерфейсы

Настоящий полиморфизм в Go достигается только через интерфейсы. Если хотите, чтобы разные «наследники» вели себя по-разному, определяйте интерфейс:

```go
package main

import "fmt"

type Speaker interface {
    Speak()
    GetName() string
}

// --- Базовое поведение ---

type Animal struct {
    Name string
}

func (a Animal) GetName() string { return a.Name }
func (a Animal) Speak() {
    fmt.Printf("%s издаёт звук\n", a.Name)
}

// --- "Наследник" Dog ---

type Dog struct {
    Animal
}

// "Переопределяем" Speak — теперь у Dog своя версия
func (d Dog) Speak() {
    fmt.Printf("%s говорит: Гав!\n", d.Name)
}

// --- "Наследник" Cat ---

type Cat struct {
    Animal
}

func (c Cat) Speak() {
    fmt.Printf("%s говорит: Мяу!\n", c.Name)
}

// --- Использование полиморфизма ---

func makeSpeak(s Speaker) {
    s.Speak()
}

func main() {
    animals := []Speaker{
        Dog{Animal{Name: "Рекс"}},
        Cat{Animal{Name: "Барсик"}},
        Animal{Name: "Неизвестное"},
    }

    for _, a := range animals {
        makeSpeak(a)
    }
}
```

**Вывод:**
```
Рекс говорит: Гав!
Барсик говорит: Мяу!
Неизвестное издаёт звук
```

Здесь `Dog` и `Cat` **удовлетворяют интерфейсу** `Speaker`, потому что имеют методы `Speak()` и `GetName()`. Причём `GetName()` им достался от встроенного `Animal` — это и есть «наследование» через встраивание. А `Speak()` каждый определяет по-своему — это «переопределение».

## 4. Опасность: «переопределение» не работает внутри базового метода

Это важный подводный камень. Посмотрите:

```go
package main

import "fmt"

type Animal struct {
    Name string
}

func (a Animal) Speak() {
    fmt.Printf("%s издаёт звук\n", a.Name)
}

// Базовый метод вызывает Speak
func (a Animal) Introduce() {
    fmt.Printf("Меня зовут %s. ", a.Name)
    a.Speak() // ❌ вызовется Animal.Speak, а не Dog.Speak!
}

type Dog struct {
    Animal
}

func (d Dog) Speak() {
    fmt.Printf("%s говорит: Гав!\n", d.Name)
}

func main() {
    d := Dog{Animal{Name: "Рекс"}}
    d.Introduce()
}
```

**Вывод:**
```
Меня зовут Рекс. Рекс издаёт звук
```

Хотя мы ожидали «Гав!». Причина: `Introduce` определён на `Animal`, получатель — `Animal`, и `a.Speak()` — статический вызов `Animal.Speak`. **В Go нет виртуальных методов**, как в Java. Это принципиальное отличие.

Чтобы добиться полиморфизма, нужно либо передавать интерфейс, либо переопределять `Introduce` в `Dog`.

## 5. Композиция вместо наследования (идиоматичный Go)

В Go часто предпочитают **явную композицию**, а не встраивание. Это делает зависимости видимыми:

```go
type Logger struct{}

func (l Logger) Log(msg string) {
    fmt.Println("[LOG]", msg)
}

// Явное поле, а не встраивание
type Service struct {
    logger Logger
}

func (s Service) DoWork() {
    s.logger.Log("работаем...")
}
```

Плюсы:
- Видно, откуда пришёл метод.
- Нет случайного «протекания» методов.
- Легче тестировать (можно подменить `logger` на интерфейс).

---

## 6. Сравнение с Java (для контраста)

| Java | Go |
| :--- | :--- |
| `class Dog extends Animal` | `type Dog struct { Animal }` |
| `super.speak()` | `d.Animal.Speak()` |
| Полиморфизм через наследование | Полиморфизм только через интерфейсы |
| Виртуальные методы по умолчанию | Виртуальных методов нет |
| `Dog` является `Animal` | `Dog` **не является** `Animal` |
| `@Override` | Просто метод с тем же именем |

---

## 7. Итог

- **В Go нет наследования.** Есть **встраивание** — это композиция, которая даёт «продвижение методов».
- Встраивание **не создаёт подтип**: `Dog` не может быть использован там, где ожидается `Animal`.
- **Полиморфизм** достигается только через **интерфейсы** с неявной реализацией.
- **Виртуальных методов нет**: базовый метод не увидит «переопределённый» метод потомка.
- Идиоматичный Go предпочитает **явную композицию** встраиванию, если нужна гибкость.

Если вы приходите из Java и хотите «наследование» в Go — забудьте про иерархии. Думайте в терминах **поведения (интерфейсы)** и **сборки из частей (композиция)**.
