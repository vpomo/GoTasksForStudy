Расскажи про опыт написания AI-агентов: 
- цепочки вызовов
- tool use / function calling
- управление состоянием агента;

Что это и приведи примеры
------


Опыт написания AI-агентов (особенно на базе LLM) кардинально отличается от обычного бэкенда. Здесь ты уже не просто пишешь `if-else`, а становишься **режиссером-оркестратором**, который управляет вниманием и инструментами нейросети.

Я разберу три кита, на которых строится любой агент, приведу код и предупрежу о подводных камнях.

---

### 1. Цепочки вызовов (Chains / Sequential Workflows)

**Что это?**  
Это жестко заданная последовательность шагов, где выход одного промпта является входом для другого. В отличие от "чистого" агента, цепочка **не имеет права выбора** — она всегда выполняет шаг А, потом Б, потом В.

**Когда использовать:** Для рутинных задач, где логика предсказуема (например, перевод текста -> краткий пересказ -> выделение ключевых сущностей).

**Пример на Python (LangChain):**

```python
from langchain.chains import LLMChain
from langchain.prompts import PromptTemplate
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4")

# Шаг 1: Генерация идеи
prompt_1 = PromptTemplate.from_template("Придумай название для стартапа, который занимается {topic}.")
chain_1 = LLMChain(llm=llm, prompt=prompt_1)

# Шаг 2: Написание слогана на основе названия
prompt_2 = PromptTemplate.from_template("Придумай слоган для стартапа с названием '{name}'.")
chain_2 = LLMChain(llm=llm, prompt=prompt_2)

# Последовательное выполнение (Chain-of-Thought исполнение)
topic = "зеленой энергетикой"
name = chain_1.run(topic)  # Первый вызов
slogan = chain_2.run(name=name)  # Второй вызов (зависит от первого)

print(f"Название: {name}\nСлоган: {slogan}")
```

**Где боль:** Цепочка не умеет возвращаться назад. Если на шаге 2 выяснилось, что название неудачное, она не перегенерирует его. Это **тупиковый граф**, поэтому для сложных задач цепочки не годятся.

### 2. Tool Use / Function Calling (Вызов функций)

**Что это?**  
Это способ дать LLM возможность "потянуться" во внешний мир. Модель не выполняет код сама — она **возвращает JSON** с именем функции и аргументами, а выполняете код уже вы (или фреймворк).

**Важнейший нюанс:** Модель — это болтун. Она хочет говорить. Если дать ей инструмент, она будет использовать его только тогда, когда это **строго необходимо** для ответа пользователю.

**Пример чистого Function Calling (OpenAI):**

Допустим, мы пишем агента для погоды. Описываем инструмент:

```python
import json
from openai import OpenAI

client = OpenAI()

# 1. Описываем инструмент для модели
tools = [{
    "type": "function",
    "function": {
        "name": "get_current_weather",
        "description": "Получить текущую погоду в городе",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "Название города"},
                "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
            },
            "required": ["city"]
        }
    }
}]

messages = [{"role": "user", "content": "Какая погода в Москве?"}]

# 2. Первый вызов API
response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages,
    tools=tools,
    tool_choice="auto"  # Модель сама решит, вызывать или нет
)

message = response.choices[0].message

# 3. Проверяем, хочет ли модель вызвать функцию
if message.tool_calls:
    tool_call = message.tool_calls[0]
    args = json.loads(tool_call.function.arguments)
    
    # 4. Мы (агент) выполняем реальный код
    if tool_call.function.name == "get_current_weather":
        # Эмуляция API
        weather_data = {"city": args["city"], "temp": "+22°C", "condition": "Солнечно"}
        
        # 5. Возвращаем результат обратно модели, чтобы она озвучила его человеку
        messages.append(message)  # добавляем запрос модели
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,
            "content": json.dumps(weather_data)
        })
        
        # 6. Финальный вызов для генерации красивого ответа пользователю
        final_response = client.chat.completions.create(
            model="gpt-4o",
            messages=messages
        )
        print(final_response.choices[0].message.content)  # "В Москве сейчас +22°C и солнечно"
```

**Опыт:** Никогда не доверяйте аргументам, которые прислала модель. Всегда валидируйте `city` через регулярку или список разрешенных городов, иначе модель может вызвать `get_current_weather(city="какой-то левый бред")`.

### 3. Управление состоянием агента (State Management)

**Что это?**  
Самая сложная часть. В отличие от HTTP-запросов (stateless), агент живет в диалоге. Состояние — это не только история сообщений (`messages`), но и:
- Выполненные шаги.
- Извлеченная информация (сущности).
- План (Plan) — что агент собирается делать дальше.
- Флаги (например, `information_gathered: false`).

**Проблема:** LLM имеет ограниченный контекст (Context Window). Вы не можете пихать всю историю бесконечно. Нужно парсить, сжимать (summarize) и хранить структурированные данные отдельно.

**Пример управления состоянием через Pydantic (без фреймворков):**

```python
from pydantic import BaseModel
from typing import List, Optional

class AgentState(BaseModel):
    user_goal: str
    chat_history: List[dict] = []  # последние N сообщений
    collected_data: dict = {}      # например, {"name": "Алексей", "age": 30}
    pending_tools: List[str] = []  # какие инструменты еще нужно вызвать
    iteration: int = 0
    is_finished: bool = False

# Логика агента с состоянием
async def run_agent(state: AgentState):
    while state.iteration < 5 and not state.is_finished:
        state.iteration += 1
        
        # 1. Формируем промпт с учетом состояния
        context = f"Цель: {state.user_goal}\nУже собрано: {state.collected_data}"
        
        # 2. Вызываем LLM
        response = get_llm_response(context, state.chat_history)
        
        # 3. Анализируем ответ и МУТИРУЕМ состояние
        if "Уточни имя" in response:
            state.pending_tools.append("ask_name")
        elif "сохраняю данные" in response:
            state.collected_data["extracted"] = "Some value"
            state.is_finished = True  # Данные получены, выходим
        
        # 4. Обрезаем историю, чтобы не переполнить контекст (State management!)
        if len(state.chat_history) > 10:
            # Оставляем только системный промпт и последние 3 сообщения
            state.chat_history = state.chat_history[-3:]  
```

**Продвинутый паттерн (Graph State):**  
В фреймворках типа **LangGraph** состояние — это глобальный словарь, который проходит через узлы (Nodes). Узлы могут принимать решение: идти в узел "Поиск_в_интернете" или в узел "Ответить_пользователю". Это называется **циклический граф**, и именно он делает агента агентом, а не цепочкой.

### Сложный пример: Связка всех трех концепций

Представьте агента-исследователя, которому дают задачу: *"Найди информацию о создателе Docker и напиши его биографию"*.

1. **Состояние:** Создаем `state = {"query": "создатель Docker", "collected_texts": [], "final_answer": ""}`.
2. **Tool Use:** Агент видит инструмент `search_google(query)`. Он вызывает его. Мы получаем текст статьи.
3. **Управление состоянием:** Мы кладем полученную статью в `collected_texts`.
4. **Chain (внутри шага):** После получения текста мы *внутри одного вызова* запускаем цепочку: *"Извлеки имена"* -> *"Найди год рождения"*.
5. **Принятие решения (Router):** Агент смотрит в состояние: *"У меня есть имя (Solomon Hykes), но нет даты смерти"*. Он решает вызвать инструмент `search_wikipedia` **повторно**, чтобы уточнить дату. Это уже не цепочка, а **цикл** (Loop).
6. Когда состояние содержит все поля, агент пишет финальный ответ и выходит.

### Главные грабли (Hard-won experience)

1. **Агент "зацикливается":** Без стоп-слов и счетчика итераций агент будет вызывать один и тот же инструмент вечно. **Всегда** ограничивайте количество шагов (max_iterations=10).
2. **Утечка состояния:** Если вы храните состояние в глобальной переменной, при одновременных запросах пользователей все перемешается. Используйте сессии (как в примере с Pydantic) или БД.
3. **Стоимость:** Function Calling + состояние = много токенов. Каждый раз вы отправляете модели описание всех инструментов (tools). Для GPT-4 это может стоить копейки за запрос. Кешируйте системные промпты.
4. **Параллельные вызовы:** Современные модели умеют вызывать **несколько функций за раз** (`parallel_tool_calls=True`). Это спасает, когда нужно и погоду узнать, и курс валют — делайте это параллельно, не ждите очереди.

**Мой совет:** Начинайте с цепочек (их проще дебажить). Как только логика перестает влезать в один промпт — переходите к графам состояний (LangGraph или CrewAI). И всегда логируйте **все** аргументы, которые модель передает в инструменты — это лучший способ понять, как она "думает".
