# 🎬 Сценарий: «Умный город» — платформа мониторинга и реагирования в реальном времени

## 📖 Легенда

Представьте город **Новоград** — современный мегаполис с населением 5 миллионов человек. В городе развернута единая платформа «Умный город», которая собирает данные с десятков тысяч датчиков, камер, светофоров и городских служб. Вся эта информация стекается в **Apache Kafka**, которая выступает «нервной системой» города. Разные сервисы подписываются на нужные потоки и реагируют на события в реальном времени.

Этот сценарий хорош тем, что показывает **сильные стороны Kafka**: высокая пропускная способность, работа с множеством независимых потребителей, хранение истории событий и потоковая обработка.

---

## 🏙️ Архитектура: действующие лица

**Источники данных (Producers):**
- 🚗 Датчики трафика на перекрестках (10 000 штук)
- 🚌 GPS-трекеры общественного транспорта (2 000 автобусов)
- 🌡️ Экологические датчики (воздух, шум, температура)
- 🚨 Системы экстренных служб (911, пожарные, скорая)
- 💡 Умные счетчики электроэнергии в домах
- 📱 Мобильное приложение горожан (жалобы, сообщения)

**Топики Kafka:**
```
traffic.events          — события с перекрестков
transport.gps           — координаты транспорта
ecology.sensors         — данные о воздухе и шуме
emergency.calls         — вызовы экстренных служб
energy.consumption      — потребление электричества
citizen.reports         — обращения жителей
city.alerts             — итоговые оповещения (создается сервисами)
```

## 🎞️ Пошаговый сценарий

### Шаг 1. Утро понедельника, 07:30 — Час пик начинается

Датчики на перекрестке ул. Ленина и пр. Мира фиксируют резкий рост числа машин. Каждые 5 секунд они отправляют событие в Kafka:

```json
{
  "intersection_id": "LEN-MIR-001",
  "timestamp": "2026-10-13T07:30:12Z",
  "vehicle_count": 342,
  "avg_speed_kmh": 12,
  "queue_length_m": 480
}
```

Продюсер (сервис сбора данных) публикует это в топик `traffic.events` с ключом `intersection_id`. Kafka записывает событие в партицию, соответствующую этому перекрестку — **все события одного перекрестка попадают в одну партицию и обрабатываются строго по порядку**.

---

### Шаг 2. Независимые потребители читают один и тот же поток

На топик `traffic.events` подписаны **четыре разные группы потребителей**, и каждая решает свою задачу:

| Consumer Group | Задача |
|---|---|
| `traffic-analytics` | Считает статистику пробок |
| `adaptive-signals` | Управляет светофорами |
| `navigation-service` | Обновляет карты для навигаторов |
| `city-dashboard` | Рисует онлайн-карту для мэрии |

👉 **Важно:** Kafka позволяет всем четырём группам читать один и тот же поток независимо. Каждая группа хранит свой offset (позицию чтения), поэтому они не мешают друг другу. Если `navigation-service` отстанет на 5 минут — он просто догонит, не влияя на остальных.

---

### Шаг 3. Потоковая обработка: Kafka Streams обнаруживает пробку

Сервис `traffic-analytics` использует **Kafka Streams** для оконной агрегации. Он анализирует скользящее окно в 2 минуты:

```java
KStream<String, TrafficEvent> stream = builder.stream("traffic.events");

stream
  .groupByKey()
  .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(2)))
  .aggregate(
      () -> new TrafficStats(),
      (key, event, stats) -> stats.add(event)
  )
  .filter((key, stats) -> stats.avgSpeed() < 10 && stats.queueLength() > 400)
  .toStream()
  .map((key, stats) -> new CityAlert(
      "TRAFFIC_JAM",
      key.key(),
      "Пробка: скорость " + stats.avgSpeed() + " км/ч"
  ))
  .to("city.alerts");
```

Через 2 минуты сервис публикует в топик `city.alerts` событие о пробке.

---

### Шаг 4. Реакция в реальном времени — цепная реакция сервисов

Топик `city.alerts` — это триггер для целого оркестра действий:

**🚦 Сервис `adaptive-signals`** читает алерт и продлевает зелёный сигнал на параллельных улицах на 20 секунд, чтобы разгрузить перекресток.

**🧭 Сервис `navigation-service`** мгновенно перестраивает маршруты для 15 000 водителей, которые сейчас едут в эту зону.

**🚌 Сервис `transport-gps`** анализирует данные автобусов и отправляет уведомление в диспетчерскую: «Автобус №42 опаздывает на 8 минут из-за пробки».

**📱 Сервис `citizen-notifications`** отправляет push-уведомления жителям, чьи маршруты проходят через проблемный участок.

**📊 Сервис `city-dashboard`** обновляет онлайн-карту мэрии — красная зона появляется на экранах у дежурных.

Все эти сервисы работают **параллельно и асинхронно**, потому что каждый из них — отдельная consumer group на топик `city.alerts`.

---

### Шаг 5. Экстренный случай: приоритетное событие

В 08:15 на перекрестке происходит ДТП. Очевидец нажимает кнопку в мобильном приложении. Событие попадает в топик `citizen.reports`:

```json
{
  "type": "ACCIDENT",
  "location": {"lat": 55.7558, "lon": 37.6173},
  "severity": "HIGH",
  "reported_by": "user_918273"
}
```

Сервис `emergency-dispatcher` читает этот поток. Благодаря **партиционированию по геохешу**, все события из одного района попадают в одну партицию — это позволяет диспетчеру видеть их в правильном порядке и быстро реагировать.

Диспетчер публикует ответное событие в `emergency.calls`, которое запускает:
- отправку скорой (через интеграцию с медицинской системой),
- перекрытие полосы (через `adaptive-signals`),
- оповещение соседних машин (через `navigation-service`).

---

### Шаг 6. Экология и энергетика — кросс-доменная аналитика

Параллельно другие топики живут своей жизнью:

- `ecology.sensors` публикует данные о качестве воздуха каждые 30 секунд с 500 датчиков.
- `energy.consumption` собирает показания 200 000 умных счётчиков.

Сервис `smart-grid-optimizer` использует **Kafka Streams join**: он объединяет поток энергопотребления с прогнозом погоды (из топика `weather.forecast`) и автоматически снижает нагрузку на сеть в часы пик.

Сервис `eco-monitor` коррелирует всплески загрязнения воздуха с данными о трафике и делает вывод: «Загрязнение в районе X вызвано пробкой на ул. Ленина».

---

### Шаг 7. Хранение истории и replay

К вечеру аналитики мэрии хотят понять, что происходило утром. Благодаря тому, что **Kafka хранит события 7 дней** (retention), они могут:

- «перемотать» любой топик на 07:30 и проиграть сценарий заново,
- обучить ML-модель прогнозирования пробок на исторических данных,
- провести аудит: кто и когда получал алерты.

Новый сервис можно подключить к любому топику и прочитать **всю историю с самого начала** — Kafka не удаляет события после прочтения, в отличие от классических очередей.

## 🎯 Почему именно Kafka здесь идеальна

| Требование | Как Kafka решает |
|---|---|
| Миллионы событий в секунду | Горизонтальное масштабирование через партиции |
| Много независимых потребителей | Consumer groups с собственными offset |
| Порядок событий по ключу | Партиционирование по `intersection_id` |
| Обработка в реальном времени | Kafka Streams, оконные агрегации |
| Хранение истории | Retention policy (дни/недели/бесконечно) |
| Повторная обработка | Replay через сброс offset |
| Связь разных доменов | Единая шина топиков для трафика, экологии, энергии |

## 🌅 Итог: один день из жизни Новограда

К 09:00 утренний час пик закончился. За это время через Kafka прошло:

- **~50 миллионов** событий о трафике,
- **~2 миллиона** GPS-координат,
- **~300 тысяч** показаний эко-датчиков,
- **~1 200** алертов,
- **~40** экстренных вызовов.

Ни один сервис не упал, ни одно событие не потерялось. Город «дышал» в реальном времени — и всё это благодаря тому, что Kafka выступила **центральной нервной системой**, а не просто очередью сообщений.
