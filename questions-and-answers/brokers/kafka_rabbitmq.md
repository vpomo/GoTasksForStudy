### Главное философское отличие

| Критерий | **RabbitMQ** | **Kafka** |
| :--- | :--- | :--- |
| **Суть** | **Брокер очередей (Queue Broker)**. Умный почтальон. | **Распределенный лог (Commit Log)**. Архивная лента событий. |
| **Семантика** | **Удаление после прочтения** (Destructive). Забрал сообщение — его нет. | **Хранение по времени** (Retention). Прочитал — сообщение остается на диске. |
| **Потребитель** | **Конкурентный** (Round-robin). Несколько воркеров делят очередь. | **Подписной** (Consumer Group). Каждый читает свою копию лога (партицию). |
| **Когда выбрать** | Передача **команд** (RPC, задачи, переводы) между сервисами. | Поток **событий** (аналитика, аудит, CDC, восстановление состояния). |

---

### Детали реализации (Golang)

1.  **RabbitMQ** — клиент отправляет сообщение с `Exchange` и `Routing Key`, брокер маршрутизирует в очередь. Потребитель через `ack` подтверждает обработку (если не подтвердил — сообщение вернется в очередь).
2.  **Kafka** — продюсер пишет в **топик** → **партицию** (ключ определяет партицию). Консьюмер читает **сдвиг (offset)**. Партиции позволяют масштабировать читателей (сколько партиций, столько воркеров в группе).

### Вымышленные примеры на Go

#### Пример 1. Система онлайн-кинотеатра ("КиноКасса")

**Задача:** Пользователь покупает билет. Нужно забронировать место, списать деньги, отправить email и напечатать чек.

- **Решение на RabbitMQ (Команды):**
    Создается одна очередь `ticket.orders`. Микросервис **Payment** забирает задачу, платит, отправляет **новое** сообщение в очередь `ticket.confirmed`. Три воркера (`Email`, `Print`, `Loyalty`) висят на этой очереди и забирают подтверждение **в режиме конкуренции** (кто первый). Если `Print` упал — сообщение вернется и будет отдано другому воркеру.

```go
// Продюсер (API Gateway)
func CreateOrder(w http.ResponseWriter, r *http.Request) {
    conn, _ := amqp.Dial("amqp://...")
    ch, _ := conn.Channel()
    ch.Publish(
        "orders.exchange", // Обменник
        "ticket.pay",      // Routing Key
        false,
        false,
        amqp.Publishing{
            Type: "task", // Команда
            Body: []byte(`{"user_id":1, "seat":"A5"}`),
            DeliveryMode: amqp.Persistent, // Не потерять при рестарте
        },
    )
}

// Консьюмер (Payment Service)
func main() {
    msgs, _ := ch.Consume("ticket.queue", "", false, false, false, false, nil)
    for d := range msgs {
        if err := processPayment(d.Body); err != nil {
            d.Nack(false, true) // Requeue (вернуть обратно в очередь)
        } else {
            d.Ack(false) // Удалить
        }
    }
}
```

#### Пример 2. Платформа аналитики для того же кинотеатра

**Задача:** Все клики пользователей, просмотры трейлеров, паузы, выходы должны попадать в **Data Lake** для построения тепловых карт. Потеря данных недопустима, но обрабатывать можно с задержкой.

- **Решение на Kafka (События):**
    Создается топик `user.actions`. Сервис **Tracker** шлет события. Три разных сервиса читают **этот же топик** независимо:
    - `RealtimeRecommender` (группа 1) — делает рекомендации здесь и сейчас.
    - `ClickHouseLoader` (группа 2) — батчами грузит в БД для отчетов.
    - `FraudDetector` (группа 3) — ищет накрутку ботов.

```go
// Продюсер (Tracker Service)
func TrackAction(userID string, action string) {
    w := sarama.NewSyncProducer([]string{"kafka:9092"}, nil)
    msg := &sarama.ProducerMessage{
        Topic: "user.actions",
        Key:   sarama.StringEncoder(userID), // Ключ гарантирует, что действия 1 юзера всегда в 1 партиции (порядок!)
        Value: sarama.StringEncoder(fmt.Sprintf(`{"ts":%d, "act":"%s"}`, time.Now().Unix(), action)),
    }
    partition, offset, _ := w.SendMessage(msg) // Ждем подтверждения записи на диск (ISR)
}

// Консьюмер (Recommender — читает только свои партиции)
func Consume() {
    consumer := sarama.NewConsumerGroup(...)
    consumer.Consume(ctx, []string{"user.actions"}, &handler{})
    // При перезапуске продолжит читать с последнего сохраненного offset
}

type handler struct{}
func (h *handler) ConsumeClaim(sess sarama.ConsumerGroupSession, claim sarama.ConsumerGroupClaim) error {
    for msg := range claim.Messages() {
        // Обработка. Если упало — просто логгируем. Offset не коммитим.
        // При рестарте прочитаем это сообщение снова (At-least-once).
        updateMLModel(msg.Value)
        sess.MarkMessage(msg, "") // Подтверждаем успех
    }
    return nil
}
```

### Ключевой момент при выборе для Go-микросервисов

- **RabbitMQ + AMQP** — идеален, когда вам нужно **балансировать нагрузку** между поднимающимися экземплярами микросервисов (например, 10 подов **Payment** разбирают очередь как пул воркеров).
- **Kafka + Sarama** — идеален, когда вам нужно **восстанавливать состояние** нового микросервиса. Если вы добавили новый сервис `UserBehaviorHistory`, он просто стартует читать топик `user.actions` с **начала времен** (`OffsetOldest`) и воссоздаст полную историю действий любого пользователя.

**Золотое правило:**
> RabbitMQ передает **задания** (сделай это прямо сейчас и удали).  
> Kafka передает **факты** (это произошло в 14:05, сохрани эту запись навсегда).


У Apache Kafka пропускная способность значительно выше, и это одно из её ключевых архитектурных преимуществ. Если говорить о цифрах, Kafka обычно работает на порядок (в 10 и более раз) быстрее, чем RabbitMQ .

### 📊 Сравнение производительности

| Характеристика | Apache Kafka | RabbitMQ |
| :--- | :--- | :--- |
| **Типичная пропускная способность** | **Сотни тысяч – миллионы** сообщений в секунду  | **Тысячи – десятки тысяч** сообщений в секунду  |
| **На что способен** | Подходит для огромных потоков данных, например, логов или событий от миллионов пользователей  | Отлично справляется с высокими нагрузками, но на меньших объемах и при сложной маршрутизации  |

Эти различия обусловлены архитектурой: Kafka оптимизирована для **записи больших пакетов данных на диск** и их **последовательного чтения**, что даёт максимальную производительность. RabbitMQ, напротив, предоставляет более гибкие сценарии маршрутизации, что требует дополнительных вычислительных затрат.

### 🔢 Откуда такие цифры?

Разница хорошо видна на реальных данных. Например, один из сравнительных обзоров показал, что Kafka может достигать пропускной способности в **1.2 миллиона сообщений в секунду** . Для RabbitMQ те же тесты зафиксировали пик производительности в **1.08 миллиона сообщений в секунду** для Go-приложения, но это было в специально оптимизированных условиях, и **устойчивая** пропускная способность была уже ниже — около **266 тысяч сообщений в секунду** . Однако это скорее исключение, подтверждающее правило, так как в большинстве сравнительных анализов Kafka стабильно показывает результаты на порядок выше, чем RabbitMQ .

Также стоит учитывать, что пропускная способность зависит от множества факторов:
*   **Размер сообщения:** Чем меньше сообщение, тем выше TPS (транзакций в секунду) .
*   **Настройки надежности:** Включение подтверждений (acks) и журналирования (persistence) снижает производительность обоих брокеров .
*   **Инфраструктура:** Производительность сильно зависит от мощности серверов, дисков и сети .

Поэтому в большинстве случаев, если ваш главный критерий — **максимальная пропускная способность** для работы с огромными потоками событий, выбор очевиден в пользу Kafka .


### 🐰 RabbitMQ + AMQP

Это комбинация **сервера очередей сообщений** и **стандартного протокола**, на котором он работает.

*   **RabbitMQ** — это популярный брокер сообщений (message broker) с открытым исходным кодом, написанный на языке Erlang. Его задача — принимать сообщения от одних приложений (продюсеров) и доставлять их другим (консьюмерам). Его часто представляют как «почтовое отделение»: он хранит сообщения в очередях и гарантирует их доставку.
*   **AMQP** (Advanced Message Queuing Protocol) — это открытый стандарт протокола прикладного уровня для обмена сообщениями. RabbitMQ изначально разрабатывался для поддержки AMQP 0-9-1, и этот протокол является «родным» для него.

**Как это работает вместе:**
RabbitMQ использует модель AMQP, которая включает в себя:
*   **Exchanges** (обменники): получают сообщения от продюсеров и маршрутизируют их в очереди на основе правил (routing keys) и типа обменника (direct, topic, fanout).
*   **Queues** (очереди): хранят сообщения до тех пор, пока их не заберут консьюмеры.
*   **Bindings** (привязки): правила, которые связывают обменники с очередями.

Помимо AMQP, RabbitMQ также поддерживает другие протоколы (MQTT, STOMP) через плагины.

### 🚀 Kafka + Sarama

Это комбинация **распределенной платформы для потоковой передачи данных** и **клиентской библиотеки для языка Go**.

*   **Apache Kafka** — это распределенная платформа для потоковой передачи событий (event streaming). В отличие от традиционного брокера очередей, Kafka работает как распределенный, реплицируемый журнал (log). Данные в Kafka хранятся в топиках (topics), которые разбиты на партиции. Это позволяет ей обрабатывать огромные объемы данных в реальном времени и обеспечивать очень высокую пропускную способность.
*   **Sarama** — это **чистая клиентская библиотека на языке Go** для работы с Apache Kafka (версии 0.8 и выше). Она предоставляет разработчикам на Go удобный API для отправки (producing) и чтения (consuming) сообщений.

**Как это работает вместе:**
Разработчик, пишущий на Go, использует библиотеку Sarama в своем коде для того, чтобы взаимодействовать с кластером Kafka. Sarama реализует протокол Kafka и предоставляет:
*   **High-level API**: Упрощенные интерфейсы, такие как `SyncProducer` (синхронная отправка) или `AsyncProducer` (асинхронная отправка), а также API для Consumer Groups.
*   **Low-level API**: Доступ к деталям протокола, если стандартных возможностей не хватает.

### 💎 Краткое резюме

| Характеристика | **RabbitMQ + AMQP** | **Kafka + Sarama** |
| :--- | :--- | :--- |
| **Что это** | Брокер сообщений + протокол | Платформа потоковой передачи + клиентская библиотека |
| **Основная модель** | Умный брокер (маршрутизация через Exchange) | Распределенный журнал (логи) |
| **Язык клиента** | Любой (Java, Python, .NET и т.д.) | Go (для библиотеки Sarama) |
| **Основное назначение** | Надежная доставка задач, RPC, сложная маршрутизация | Потоковая обработка данных, сбор логов, event sourcing |

Если говорить упрощенно: **RabbitMQ** — это про умную и гибкую доставку отдельных сообщений, а **Kafka** — про высокоскоростную обработку непрерывных потоков событий. **Sarama** в этой связке — это просто «пульт управления» для Kafka на языке Go.
