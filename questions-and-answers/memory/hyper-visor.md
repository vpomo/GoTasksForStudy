** Что такое контейнеры, ВМ? отличие ВМ от контейнера, виды гипервизоров?**

---

### 1. Что такое Виртуальные Машины (ВМ)?

**Виртуальная машина** — это программная эмуляция физического компьютера. Она имитирует аппаратное обеспечение: CPU, память, диски, сетевые карты.

**Архитектура:**
1.  **Hypervisor** (гипервизор) — прослойка.
2.  **Guest OS** (гостевая ОС) — полноценная операционная система (Linux, Windows), которая работает поверх гипервизора. Она включает в себя свое ядро.
3.  **Hardware** — физическое железо хост-машины.

**Ключевая характеристика:** ВМ запускает **полную ОС**. Это обеспечивает высокий уровень изоляции (граница проходит на уровне ядра), но накладывает накладные расходы на память и дисковое пространство (гостевая ОС может занимать гигабайты).

---

### 2. Что такое Контейнеры?

**Контейнер** — это изолированная среда выполнения процесса на уровне операционной системы. В отличие от ВМ, контейнер не эмулирует железо и не содержит своей ОС. Он использует ядро *хостовой* ОС.

**Архитектура:**
1.  **Container Runtime** (Docker, containerd, CRI-O) — управляет жизненным циклом.
2.  **Container Image** — слой файловой системы (обычно SquashFS или overlayfs), содержащий приложение и его зависимости (библиотеки, бинарные файлы), но **без** ядра.
3.  **Host OS** — единственное ядро, работающее на физическом сервере.

**Изоляция реализуется через механизмы ядра Linux:**
*   **Namespaces:** Ограничивают видимость. Процесс внутри контейнера видит свою сеть (net), дерево процессов (pid), пользователей (user), файловую систему (mount) так, как будто он один на сервере.
*   **Cgroups (Control Groups):** Ограничивают ресурсы. Позволяют жестко задать, сколько CPU, RAM или IOPS может потребить группа процессов (контейнер).

---

### 3. Отличия ВМ от Контейнеров

Это самый частый вопрос. Вот сравнительная таблица с точки зрения архитектуры и эксплуатации:

| Характеристика | Виртуальная Машина (VM) | Контейнер |
| :--- | :--- | :--- |
| **Изоляция** | Полная аппаратная изоляция (тяжелая граница) | Изоляция на уровне процессов (легкая граница). Если ядро хоста падает — падают все контейнеры. |
| **Время запуска** | Минуты (загрузка BIOS, инициализация ядра ОС) | Миллисекунды или секунды (запуск просто процесса) |
| **Размер** | Гигабайты (ОС + диски) | Мегабайты (только бинарники + зависимости) |
| **Переносимость** | Высокая, но тяжелая. VM образ привязан к типу гипервизора. | Высокая. Контейнер работает везде, где есть Linux (или Windows контейнеры на Windows). |
| **Потребление ресурсов** | Высокие оверхед. Каждая ВМ резервирует память и CPU для своей ОС. | Низкие. Оверхед связан только с процессами самого приложения (runtime). |
| **Управление** | Hypervisor (vSphere, KVM) | Orchestrator (Kubernetes, Docker Swarm) |

**Важное уточнение для Go-разработчика:**
Go компилируется в статически связанный бинарный файл (`CGO_ENABLED=0`). Такой бинарник не требует даже `libc` (стандартной библиотеки Си) внутри контейнера. Поэтому образы Go-приложений часто собираются на базе `scratch` (пустой образ) и весят **менее 10 МБ**, что делает контейнеры для Go абсолютным стандартом де-факто. ВМ для такого приложения — это огромный перерасход ресурсов.

### 4. Виды гипервизоров

Гипервизор — это то, что делает возможными виртуальные машины. Он делится на два типа:

#### Тип 1 (Bare-metal / нативной железный)
Гипервизор устанавливается непосредственно на физическое оборудование (железо), минуя хост-ОС. Он сам является минимальной операционной системой (microkernel).

*   **Как работает:** Гипервизор напрямую управляет железом (CPU, памятью) и распределяет ресурсы между гостевыми ОС.
*   **Производительность:** Максимальная, близкая к нативной. Нет прослойки в виде хостовой ОС.
*   **Примеры:** **VMware ESXi**, **Microsoft Hyper-V**, **KVM** (Linux Kernel-based Virtual Machine — формально KVM — это модуль ядра Linux, превращающий его в гипервизор типа 1), **Xen**.
*   **Где используется:** Дата-центры, облачные провайдеры (AWS, Google Cloud).

#### Тип 2 (Hosted / хостовой)
Гипервизор работает как обычное приложение (процесс) внутри уже установленной хост-операционной системы (Windows, macOS, Linux).

*   **Как работает:** Запросы гостевой ОС проходят через гипервизор к хост-ОС, а затем к железу.
*   **Производительность:** Есть накладные расходы на хост-ОС. Подходит для разработки, тестирования, но не для высоконагруженных продакшн-систем.
*   **Примеры:** **Oracle VirtualBox**, **VMware Workstation / Fusion**, **Parallels Desktop**.

### 5. Бонус: Что такое "Контейнеры" технически (для углубленного ответа)

Если на собеседовании спросят "А что внутри контейнера?", как сеньор вы должны ответить, что это не виртуализация, а **изоляция ресурсов**.

С точки зрения хостовой ОС, контейнер — это просто обычный процесс (или группа процессов) с набором флагов:
1.  **chroot / pivot_root:** Изменение корневой директории. Процесс не видит файловую систему хоста, только свой образ.
2.  **Namespace:** Процесс видит свои собственные сетевые интерфейсы (`eth0`), свою таблицу процессов (PID 1 внутри контейнера — это процесс, а на хосте у него может быть PID 9834).
3.  **Seccomp / AppArmor / SELinux:** Ограничение системных вызовов (syscalls). Это критично для безопасности. Например, процессу внутри контейнера можно запретить вызов `reboot` или изменение системного времени.

**Почему это важно для Go?**
Go рантайм активно использует многопоточность (goroutines) и системные вызовы. На собеседовании могут спросить: *"Что будет, если запустить Go приложение в контейнере без ограничений cgroups?"*.
Ответ: Оно может "увидеть" все CPU хоста и попытаться использовать их все, что приведет к деградации соседей. Поэтому в Go-микросервисах критически важно настроить `GOMAXPROCS` в соответствии с лимитами контейнера (современные версии Go умеют определять cgroups автоматически, но это хорошая тема для дискуссии).

### Резюме для собеседования

Если хотите блеснуть, сформулируйте суть так:
> "Главное архитектурное отличие заключается в уровне абстракции. **ВМ абстрагирует железо**, предоставляя полноценную ОС, что дает максимальную изоляцию ценой оверхеда. **Контейнер абстрагирует ОС**, изолируя лишь процесс с помощью пространств имен и cgroups, используя общее ядро. Поэтому контейнеры легковесны и идеальны для микросервисов, особенно написанных на Go, где финальный артефакт — это статический бинарник. Гипервизоры же делятся на Type 1 (KVM, ESXi) для продакшн-инфраструктуры и Type 2 (VirtualBox) для локальной разработки."

**Что такое cgroups?**
Отличный вопрос! cgroups — это фундаментальный механизм ядра Linux, который лежит в основе работы контейнеров. Как сеньор-разработчик, вы должны понимать не только теорию, но и практические аспекты работы с ними, особенно в контексте Go-приложений.

---

## 1. Что такое cgroups?

**cgroups (Control Groups)** — это механизм ядра Linux, который позволяет **ограничивать, учитывать и изолировать** использование ресурсов (CPU, память, дисковый I/O, сеть и т.д.) для группы процессов.

Проще говоря, cgroups отвечают за **обеспечение ресурсами**, в то время как namespaces отвечают за **изоляцию видимости**.

### Основные возможности:
- **Лимитирование (Limiting):** Задать максимальное количество ресурсов, которое может использовать группа.
- **Приоритизация (Prioritization):** Распределять ресурсы между группами (например, одной группе отдать больше CPU).
- **Учет (Accounting):** Отслеживать, сколько ресурсов реально потребляет группа.
- **Контроль (Control):** Возможность приостанавливать, возобновлять или завершать группу процессов.

---

## 2. Версии cgroups

На собеседовании важно показать знание эволюции этого механизма:

| Характеристика | cgroups v1 | cgroups v2 |
|:---|:---|:---|
| **Статус** | Устаревшая, но до сих пор широко используется | Современная, унифицированная версия |
| **Архитектура** | Иерархия контроллеров. Каждый контроллер имеет свою отдельную иерархию (например, `memory`, `cpu` — в разных деревьях) | Единая унифицированная иерархия. Все контроллеры в одном дереве |
| **Управление** | Сложно применять ограничения одновременно по нескольким ресурсам | Простое управление через один `/sys/fs/cgroup` |
| **Безопасность** | Меньше изоляции между контроллерами | Улучшенная безопасность и избегание конфликтов |
| **Статус** | Поддержка сохраняется для обратной совместимости | Стандарт в современных дистрибутивах (systemd интегрирован с cgroups v2) |

## 3. Основные контроллеры cgroups

Это нужно знать, чтобы понимать, что именно ограничивают контейнеры:

| Контроллер | Назначение | Ключевые файлы/параметры |
|:---|:---|:---|
| **cpu** | Ограничение процессорного времени | `cpu.shares` (приоритет), `cpu.cfs_period_us` + `cpu.cfs_quota_us` (жесткий лимит) |
| **memory** | Ограничение и учет памяти | `memory.limit_in_bytes`, `memory.usage_in_bytes`, `memory.oom_control` |
| **cpuset** | Привязка к конкретным ядрам CPU | `cpuset.cpus`, `cpuset.mems` |
| **blkio** | Ограничение I/O на диски | `blkio.throttle.read_bps_device`, `blkio.weight` |
| **net_cls, net_prio** | Маркировка сетевого трафика | Тегирование пакетов для QoS |
| **pids** | Ограничение количества процессов | `pids.max`, `pids.current` (важно для предотвращения fork-бомб) |
| **freezer** | Приостановка/возобновление процессов | `freezer.state` |
| **hugetlb** | Ограничение huge pages | Для работы с большими страницами памяти |

## 4. Как это работает на практике (иерархия)

cgroups организованы в виде иерархической файловой системы в `/sys/fs/cgroup/`.

### Для cgroups v1:
```bash
/sys/fs/cgroup/
├── cpu/
│   ├── docker/
│   │   └── <container_id>/
│   │       ├── cpu.shares
│   │       └── cpu.cfs_quota_us
├── memory/
│   ├── docker/
│   │   └── <container_id>/
│   │       └── memory.limit_in_bytes
└── ...
```

### Для cgroups v2 (унифицированная иерархия):
```bash
/sys/fs/cgroup/
├── system.slice/
├── user.slice/
├── docker/
│   └── <container_id>/
│       ├── cpu.max          # унифицированный файл для CPU
│       ├── memory.max       # унифицированный файл для памяти
│       └── pids.max
```

## 5. Практический пример: как Docker использует cgroups

Когда вы запускаете контейнер с ограничениями:
```bash
docker run --cpus="1.5" --memory="512m" --memory-swap="1g" myapp
```

Docker runtime (containerd/runc) создает cgroup для этого контейнера и записывает значения:

**Для cgroups v1:**
```bash
# CPU: 1.5 ядра (используя CFS quota)
echo "150000" > /sys/fs/cgroup/cpu/docker/<container_id>/cpu.cfs_quota_us
echo "100000" > /sys/fs/cgroup/cpu/docker/<container_id>/cpu.cfs_period_us

# Память: 512 MB
echo "536870912" > /sys/fs/cgroup/memory/docker/<container_id>/memory.limit_in_bytes
```

**Для cgroups v2:**
```bash
echo "150000 100000" > /sys/fs/cgroup/docker/<container_id>/cpu.max
echo "536870912" > /sys/fs/cgroup/docker/<container_id>/memory.max
```

## 6. Особенности для Go-разработчика (важно на собеседовании!)

### Проблема: Go runtime и cgroups

До Go 1.18 (и особенно до 1.19) Go runtime **не умел** автоматически определять cgroup-лимиты. Это приводило к серьезным проблемам:

```go
// Проблема: приложение видит все CPU хоста, а не лимит контейнера
runtime.GOMAXPROCS(0) // возвращал количество CPU на хосте, а не в контейнере!
```

**Последствия:**
- Go runtime запускал количество системных потоков (P) равное количеству CPU хоста
- При лимите в 1 CPU, но 96 ядрах на хосте, рантайм создавал 96 потоков
- Избыточная конкуренция за CPU, частые переключения контекста
- Приложение работало медленнее, чем если бы было ограничено правильно

### Решения:

**1. Ручная настройка (устаревший подход):**
```go
// В коде приложения
import "runtime"

func init() {
    // Неправильно!
    // runtime.GOMAXPROCS(2)
    
    // Правильно: устанавливать на основе переменной окружения
    if cpuLimit := os.Getenv("GOMAXPROCS"); cpuLimit != "" {
        // парсим и устанавливаем
    }
}
```

**2. Использование библиотеки automaxprocs (рекомендованный подход до Go 1.19):**
```go
import _ "go.uber.org/automaxprocs"

func main() {
    // automaxprocs автоматически определит cgroup-лимиты 
    // и установит GOMAXPROCS в init()
}
```

**3. Начиная с Go 1.19+ (и особенно 1.21+):**
Go runtime научился читать cgroups v2 и v1 автоматически:
```go
// Go 1.21+: runtime.GOMAXPROCS(0) возвращает корректное значение,
// учитывающее cgroup-лимиты CPU
procs := runtime.GOMAXPROCS(0) // вернет лимит CPU из cgroups
```

### Проверка в коде:
```go
package main

import (
    "fmt"
    "runtime"
    "runtime/debug"
)

func main() {
    fmt.Printf("GOMAXPROCS: %d\n", runtime.GOMAXPROCS(0))
    
    // Получение информации о cgroups (Go 1.20+)
    if debug.SetMemoryLimit(-1) != 0 {
        fmt.Println("Go runtime detected memory limit from cgroups")
    }
}
```

## 7. OOM Killer и memory cgroups

Важный момент для production-систем:

Когда процесс в контейнере превышает `memory.limit_in_bytes`:
1. Ядро сначала пытается освободить память (cache, swap)
2. Если не удается — активируется **OOM Killer** для этой cgroup
3. OOM Killer завершает процесс (обычно с сигналом SIGKILL)

**Для Go-приложений это критично**, потому что:
- Go runtime активно использует GC и может создавать пиковые нагрузки памяти
- Нужно настраивать `GOGC` и `GOMEMLIMIT` (Go 1.19+) для плавной работы с ограничениями

```go
import "runtime/debug"

func init() {
    // Установка мягкого лимита памяти (Go 1.19+)
    debug.SetMemoryLimit(400 * 1024 * 1024) // 400 MB
    
    // Настройка GC (по умолчанию 100%)
    debug.SetGCPercent(100)
}
```

## 8. Типичные вопросы на собеседовании

**Вопрос:** "Что произойдет, если запустить контейнер без ограничения памяти?"

**Ответ:** Контейнер сможет использовать всю доступную память хоста. Если приложение начнет потреблять всю память, OOM Killer может завершить либо сам контейнер, либо другие процессы на хосте, что приведет к нестабильности всей системы.

---

**Вопрос:** "Как проверить, в каких cgroups находится процесс?"

**Ответ:**
```bash
# Просмотр cgroups для конкретного PID
cat /proc/<PID>/cgroup

# Для docker контейнера
docker inspect <container_id> | grep -i cgroup
docker run --rm alpine cat /proc/self/cgroup
```

---

**Вопрос:** "В чем разница между `cpu.shares` и `cpu.cfs_quota_us`?" 

**Ответ:**
- **cpu.shares** — мягкий лимит, определяет приоритет при конкуренции за CPU. Если система не нагружена, процесс может использовать больше.
- **cpu.cfs_quota_us/period_us** — жесткий лимит. Например, `quota=50000`, `period=100000` означает, что процесс не может использовать больше 50% одного ядра CPU.

**Расскажи про  namespaces**
Отлично! После cgroups логично перейти к namespaces — это вторая половина фундамента контейнеризации. Если cgroups отвечают за **"сколько можно"**, то namespaces — за **"что видно"**. Давайте разберем этот механизм подробно, как и положено сеньор-разработчику.

---

## 1. Что такое namespaces?

**Namespaces** — это механизм ядра Linux, который позволяет **изолировать и виртуализировать глобальные ресурсы системы** для группы процессов. Каждый процесс в системе принадлежит какому-то namespace, и видит только те ресурсы, которые находятся в его namespace.

Простыми словами: namespaces создают иллюзию для процесса, что он работает на отдельной системе, хотя физически это один хост.

### Ключевая идея:
- Процесс в контейнере видит свою собственную файловую систему, свои сетевые интерфейсы, свою таблицу процессов
- Но на хосте это всё — просто изолированные представления одного и того же физического ресурса

---

## 2. Типы namespaces (7 видов)

В современном Linux существует 7 типов namespaces. Каждый изолирует свой аспект системы:

| Тип | Флаг | Изолируемый ресурс | Глобальный аналог |
|:---|:---|:---|:---|
| **Mount** | `CLONE_NEWNS` | Точки монтирования файловой системы | `/proc/mounts` |
| **PID** | `CLONE_NEWPID` | Идентификаторы процессов | Таблица процессов, PID 1 |
| **Network** | `CLONE_NEWNET` | Сетевые интерфейсы, маршруты, правила | `eth0`, `iptables`, порты |
| **User** | `CLONE_NEWUSER` | Пользователи и группы | `/etc/passwd`, UID/GID |
| **UTS** | `CLONE_NEWUTS` | Hostname и domainname | `hostname`, domainname |
| **IPC** | `CLONE_NEWIPC` | Межпроцессное взаимодействие | System V IPC, POSIX message queues |
| **Cgroup** | `CLONE_NEWCGROUP` | Пути к cgroups | `/sys/fs/cgroup` (v2) |

## 3. Подробный разбор каждого типа

### 3.1 Mount Namespace (CLONE_NEWNS)

**Самый первый namespace, появился в 2002 году.**

Изолирует точки монтирования. Процессы в разных mount namespaces видят разные файловые системы.

**Как работает:**
```bash
# Процесс в изолированном mount namespace
mount --make-rprivate /
mount --bind /container/rootfs /newroot
pivot_root /newroot /oldroot
# Теперь процесс видит только /container/rootfs как корневую файловую систему
```

**Ключевые особенности:**
- Каждый контейнер имеет свой mount namespace
- Изменения (mount/umount) в одном namespace не видны в других
- Поддерживает "пропагацию" монтирований (private, shared, slave, unbindable)

**Для Docker:** 
```bash
# В контейнере вы видите только его файловую систему
docker run alpine ls /  # видит только образ alpine
ls /                    # на хосте видит совсем другое
```

---

### 3.2 PID Namespace (CLONE_NEWPID)

**Изолирует дерево процессов.**

Внутри PID namespace процесс может иметь PID=1 (init), даже если на хосте у него PID=12345. Это критически важно для контейнеров, так как процесс с PID=1 получает особые привилегии (обработка сигналов, сбор зомби-процессов).

**Иерархия:**
```
Хост (root PID namespace)
├── PID 12345 (docker-containerd)
│   └── PID 12346 (runc)
│       └── Контейнер A (дочерний PID namespace)
│           ├── PID 1 (приложение внутри контейнера)
│           └── PID 2 (дочерний процесс)
└── PID 23456 (docker-containerd)
    └── Контейнер B (другой PID namespace)
        └── PID 1 (другое приложение)
```

**Важные нюансы:**
- Процесс видит только процессы внутри своего PID namespace
- PID 1 внутри namespace получает специальную обработку сигналов
- При уничтожении PID 1, ядро завершает весь namespace

**Go-специфика:**
```go
// В Go приложении внутри контейнера
pid := os.Getpid()  // вернет 1 (если это главный процесс)
ppid := os.Getppid() // вернет 0 (нет родителя в этом namespace)

// На хосте этот же процесс имеет реальный PID
```

---

### 3.3 Network Namespace (CLONE_NEWNET)

**Самый важный для микросервисов. Изолирует сетевой стек.**

Каждый network namespace имеет:
- Собственные сетевые интерфейсы (lo, eth0, veth...)
- Собственные IP-адреса
- Собственную таблицу маршрутизации
- Собственные правила iptables/netfilter
- Собственный сокет-порт (можно слушать порт 80 в каждом namespace)

**Как это реализовано в Docker:**
```bash
# На хосте создается виртуальная Ethernet пара (veth)
# Один конец помещается в network namespace контейнера
# Другой конец подключается к bridge (docker0)

# В контейнере
docker run alpine ip addr show
# 1: lo: ... 
# 2: eth0@if123: ...  # это один конец veth пары
```

**Практическое значение:**
- Контейнеры могут иметь одинаковые IP-адреса (172.17.0.0/16)
- Порт 80 может быть занят в сотне контейнеров одновременно
- Изоляция на уровне L2/L3

**Go-специфика:**
```go
// Приложение в контейнере может слушать порт 8080
server := &http.Server{Addr: ":8080"}
// На хосте этот порт не занят, т.к. он в другом network namespace
go server.ListenAndServe()
```

---

### 3.4 User Namespace (CLONE_NEWUSER)

**Изоляция пользователей и групп. Самый важный для безопасности.**

Позволяет процессу внутри namespace иметь root-привилегии (UID 0), но при этом на хосте быть обычным непривилегированным пользователем (UID 1000).

**Механизм отображения (mapping):**
```
Внутри namespace:  UID 0 (root)
    ↓ mapping
На хосте:          UID 1000 (обычный пользователь)
```

**Как это работает:**
```bash
# Создаем user namespace с отображением
echo "0 1000 1" > /proc/$$/uid_map
# Теперь процесс внутри может делать "root" вещи
# Но на хосте это обычный пользователь
```

**Безопасность:**
- root в контейнере ≠ root на хосте (если не используется `--privileged`)
- Позволяет запускать контейнеры без реальных root-привилегий
- В Docker по умолчанию user namespace отключен для совместимости, но может быть включен

**Важно для Go:**
```go
// Проверка на root внутри контейнера
if os.Geteuid() == 0 {
    fmt.Println("I'm root inside container!")
}
// На хосте этот процесс может быть обычным пользователем
```

---

### 3.5 UTS Namespace (CLONE_NEWUTS)

**UTS = UNIX Time-sharing System. Изолирует hostname и domainname.**

Позволяет каждому контейнеру иметь собственное имя хоста.

```bash
# Контейнер A
docker run --hostname=web-server-1 alpine hostname
# web-server-1

# Контейнер B
docker run --hostname=db-server-1 alpine hostname
# db-server-1

# На хосте
hostname
# production-host
```

**Применение:**
- Логи приложения пишут правильное имя сервиса
- Мониторинг может идентифицировать контейнер по hostname
- Некоторые приложения зависят от hostname

---

### 3.6 IPC Namespace (CLONE_NEWIPC)

**Изолирует механизмы межпроцессного взаимодействия:**
- System V semaphores
- System V shared memory
- POSIX message queues

**Зачем нужно:**
- Предотвращает конфликты IPC-ресурсов между контейнерами
- Безопасность — один контейнер не может влиять на IPC другого
- Позволяет использовать IPC внутри контейнера как на отдельной системе

**Пример ограничения:**
```bash
# В контейнере A создаем shared memory
ipcmk -M 1024
# В контейнере B не видно этой shared memory
ipcs -m  # пусто
```

---

### 3.7 Cgroup Namespace (CLONE_NEWCGROUP)

**Самый новый (Linux 4.6, 2016). Виртуализирует путь к cgroups.**

Позволяет процессу видеть только свои собственные cgroups, а не всю иерархию системы.

**До cgroup namespace:**
```bash
# В контейнере можно было видеть все cgroups хоста
cat /proc/self/cgroup
# 12:memory:/docker/abc123...
# 11:cpu:/docker/abc123...
```

**После cgroup namespace:**
```bash
# Процесс видит только свой поддерево
cat /proc/self/cgroup
# 12:memory:/
# 11:cpu:/
```

**Значение:**
- Безопасность — контейнер не может видеть cgroups других контейнеров
- Для мониторинга внутри контейнера — видит только свои ограничения
- Go runtime может корректно определять лимиты

## 4. Как это всё связывается вместе (создание контейнера)

Процесс создания контейнера (упрощенно):

```c
// Псевдокод создания контейнера (runc, crun)

// 1. Создаем новый процесс с набором namespace
int flags = CLONE_NEWNS | CLONE_NEWPID | CLONE_NEWNET | 
            CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWUSER;

pid_t container_pid = clone(child_func, stack, flags, NULL);

// 2. Настраиваем user namespace mapping
write_uid_map(container_pid, "0 1000 1");
write_gid_map(container_pid, "0 1000 1");

// 3. Настраиваем network namespace
// Создаем veth пару, перемещаем один конец в network namespace

// 4. Настраиваем mount namespace
// pivot_root в корень контейнера

// 5. Запускаем процесс
execve("/bin/myapp", args, env);
```

## 5. Практическая демонстрация

Создадим изолированный процесс вручную (без Docker):

```bash
# Создаем новый mount и PID namespace
sudo unshare --mount --pid --fork --mount-proc /bin/bash

# Теперь внутри нового namespace
echo $$  # PID 1 внутри namespace
mount  # видим только изолированные точки монтирования
ps aux # видим только процессы внутри namespace

# Добавляем сетевую изоляцию
sudo unshare --net /bin/bash
ip addr show # только loopback, нет eth0

# Поднимаем loopback
ip link set lo up
```

## 6. Namespaces и безопасность

**Критически важно для собеседования:**

| Риск | Описание | Решение |
|:---|:---|:---|
| **Namespace escape** | Возможность выйти из namespace | User namespaces + seccomp + AppArmor |
| **Kernel exploits** | Уязвимости в системных вызовах | Seccomp фильтры, ограничение syscalls |
| **Shared resources** | /proc, /sys все еще частично общие | Монтирование специфических файловых систем |
| **CAP_SYS_ADMIN** | Много привилегий в одном флаге | Drop всех capabilities, добавление только нужных |

**Docker security best practices:**
```bash
# Запуск с ограничениями
docker run \
  --cap-drop=ALL \
  --cap-add=NET_BIND_SERVICE \
  --security-opt=no-new-privileges \
  --security-opt=seccomp=/path/to/seccomp.json \
  myapp
```

## 7. Go-специфика: работа с namespaces

### Проверка namespace процесса:
```go
package main

import (
    "fmt"
    "os"
    "syscall"
)

func main() {
    // Проверка, в каком PID namespace мы находимся
    stat, _ := os.Stat("/proc/self/ns/pid")
    fmt.Printf("PID namespace inode: %v\n", stat.Sys())
    
    // Получение списка namespace
    namespaces := []string{
        "pid", "user", "net", "mnt", "uts", "ipc",
    }
    
    for _, ns := range namespaces {
        path := fmt.Sprintf("/proc/self/ns/%s", ns)
        if link, err := os.Readlink(path); err == nil {
            fmt.Printf("%s: %s\n", ns, link)
        }
    }
    
    // Проверка, являемся ли мы PID 1 в своем namespace
    if os.Getpid() == 1 {
        fmt.Println("I am PID 1 in this PID namespace")
    }
}
```

### Создание нового namespace (требует root):
```go
package main

import (
    "os"
    "os/exec"
    "syscall"
)

func main() {
    cmd := exec.Command("/bin/bash")
    cmd.SysProcAttr = &syscall.SysProcAttr{
        Cloneflags: syscall.CLONE_NEWNS |
            syscall.CLONE_NEWPID |
            syscall.CLONE_NEWNET |
            syscall.CLONE_NEWUTS |
            syscall.CLONE_NEWIPC,
    }
    cmd.Stdin = os.Stdin
    cmd.Stdout = os.Stdout
    cmd.Stderr = os.Stderr
    
    if err := cmd.Run(); err != nil {
        panic(err)
    }
}
```

## 8. Типичные вопросы на собеседовании

**Вопрос:** "Почему процесс внутри контейнера не может видеть процессы хоста?"

**Ответ:** Потому что он запущен в отдельном PID namespace. Ядро Linux скрывает процессы из родительских namespaces. При создании контейнера runtime (runc) устанавливает флаг `CLONE_NEWPID`, создавая изолированное дерево процессов, где приложение становится PID 1.

---

**Вопрос:** "Можно ли из контейнера получить доступ к сети хоста?"

**Ответ:** Да, если контейнер запущен в host network namespace (`docker run --net=host`). Тогда контейнер использует сетевой стек хоста напрямую, что дает лучшую производительность, но снижает изоляцию. Также можно через проброс портов или прямой доступ к интерфейсам.

---

**Вопрос:** "Что опаснее: user namespace или mount namespace с точки зрения безопасности?"

**Ответ:** User namespace — наиболее критичен для безопасности. Если злоумышленник сможет выйти из user namespace с привилегиями root, он получит полный доступ к хосту. Mount namespace сам по себе не дает привилегий, но в комбинации с другими может быть опасен. Именно поэтому Docker по умолчанию не использует user namespace для упрощения, но для production рекомендуется включать.

---

**Вопрос:** "Как проверить, в каких namespaces работает процесс?"

**Ответ:**
```bash
# Просмотр ссылок на namespace
ls -la /proc/<PID>/ns/

# Сравнение namespace двух процессов
ls -la /proc/1234/ns/net
ls -la /proc/5678/ns/net
# Если inode одинаковый — процессы в одном namespace
```

## 9. Namespaces vs cgroups: итоговое сравнение

| Характеристика | Namespaces | cgroups |
|:---|:---|:---|
| **Назначение** | Изоляция видимости | Ограничение ресурсов |
| **Что изолирует** | PID, сеть, файловую систему, пользователей | CPU, память, I/O, pids |
| **Ключевая метафора** | "Что видит процесс" | "Сколько может съесть" |
| **Безопасность** | Предотвращает доступ к чужим ресурсам | Предотвращает DoS |
| **Взаимодействие** | Работают независимо | Работают независимо |

## Резюме для собеседования

> "Namespaces — это механизм изоляции ядра Linux, который позволяет процессу иметь свой собственный вид глобальных системных ресурсов. Существует 7 типов namespaces: Mount (изоляция файловой системы), PID (дерево процессов), Network (сетевой стек), User (пользователи), UTS (hostname), IPC (межпроцессное взаимодействие) и Cgroup (виртуализация cgroups). Вместе с cgroups, которые ограничивают ресурсы, namespaces формируют полную изоляцию контейнера. В Go-приложениях важно понимать, в каком namespace мы работаем, особенно при работе с PID 1 (обработка сигналов) и network namespace (сетевое взаимодействие). Безопасность контейнеров во многом зависит от правильной конфигурации namespaces и ограничения capabilities."
