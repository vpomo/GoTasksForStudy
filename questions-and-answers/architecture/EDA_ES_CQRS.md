## Что такое event-driven архитектура? 

---

### 1. Определение (Суть)

**Event-Driven Architecture (EDA)** — это архитектурный паттерн, в котором поток выполнения программы определяется событиями. Вместо того чтобы сервис А напрямую вызывал сервис Б (синхронный REST/gRPC), сервис А публикует **событие** (факт произошедшего действия), а сервис Б реагирует на это событие асинхронно.

**Ключевая фишка:** Производитель (Producer) не знает, кто и как будет обрабатывать событие. Связь между сервисами — **слабая** (loose coupling).

---

### 2. Основные компоненты (Структура)

В любой EDA есть 4 главных элемента:

1.  **Событие (Event):** Неизменяемый факт. Например, `OrderCreated`, `UserRegistered`. Важно: событие — это **глагол в прошедшем времени**.
2.  **Производитель (Producer):** Генерирует событие и отправляет его в брокер.
3.  **Брокер/Шина (Broker/Message Queue):** Промежуточный слой (Kafka, RabbitMQ, NATS). Хранит события и управляет очередями.
4.  **Потребитель (Consumer):** Слушает брокера, получает событие и выполняет свою бизнес-логику (например, отправляет письмо или начисляет бонусы).

---

### 3. Когда это нужно (Проблемы, которые решает)

Здесь важно сказать, что EDA — это не серебряная пуля. Её используют, если:

*   **Асинхронность:** Нам не нужно ждать ответа прямо сейчас (например, отправка SMS после заказа).
*   **Масштабируемость:** Нагрузка неравномерна. Если ночью заказов мало, потребитель спит. В черную пятницу — поднимаем 10 инстансов консьюмеров (competing consumers).
*   **Сложные бизнес-процессы:** Саги (Sagas) для распределенных транзакций.
*   **Интеграция гетерогенных систем:** Системы на Java, Python и Go общаются через общий брокер, не завязываясь на HTTP-контракты друг друга.

---

### 4. Плюсы и Минусы (Обязательно упомянуть, это показывает опыт)

**Плюсы:**
*   Слабая связанность (изменяем один сервис без остановки других).
*   Отказоустойчивость (брокер хранит события, если потребитель упал — он дочитает их после перезапуска).
*   Легкость горизонтального масштабирования.

**Минусы:**
*   **Сложность отладки:** Трассировка запроса превращается в квест (нужен Distributed Tracing — Jaeger).
*   **Гарантии доставки:** At-least-once (дубли) или Exactly-once (сложно). Придется делать идемпотентность потребителей.
*   **Eventual Consistency (Конечная согласованность):** Данные не обновляются мгновенно. Пользователь может увидеть статус "Processing", а не мгновенный успех.
*   **Смертельная проблема:** Появление **Dead Letter Queue** (неправильный формат события) может "засорить" всю систему, если не настроить мониторинг.

---

### 5. Особенности реализации в Go (Самый важный блок для сеньоров)

Здесь нужно показать, что ты не просто знаешь теорию, а умеешь писать код.

*   **Брокеры:** В Go-комьюнити чаще всего используют **NATS** (легкий, быстрый, встроенный JetStream для persistence) или **Kafka** (через библиотеку `segmentio/kafka-go` или `IBM/sarama`). RabbitMQ используют реже из-за AMQP-оверхеда.
*   **Работа с контекстом:** Обязательно используй `context.WithTimeout` в хендлерах потребителя, чтобы долгие обработки не вешали партицию (в Kafka) или не блокировали ack (в NATS).
*   **Паттерн Worker Pool:** В Go легко реализовать пул воркеров. Получаем события из канала (`<-ch`) и отдаем в пул горутин. Это повышает пропускную способность, не плодя тысячи горутин на каждое сообщение.
*   **Идемпотентность:** Так как в EDA доставка часто `At-least-once`, в Go-сервисе мы обязаны проверять дубли. Решение: хранить `messageID` в Redis (`SETNX`) с TTL, чтобы отсекать повторы при перечитывании партиции.

**Пример кода (Идемпотентность):**
```go
func (h *Handler) ProcessEvent(ctx context.Context, msg *Message) error {
    // Используем Redis как распределенный локер для защиты от дублей
    ok, err := h.redis.SetNX(ctx, "processed:"+msg.ID, "1", 10*time.Minute).Result()
    if err != nil {
        return err // Не паникуем, дадим брокеру переотправить позже
    }
    if !ok {
        log.Info("duplicate event, skipping")
        return nil // Подтверждаем (ack), чтобы не застрять в цикле
    }

    // Выполняем бизнес-логику (изменение БД)
    return h.repo.SaveOrder(ctx, msg.Payload)
}
```

*   **Graceful Shutdown:** Обязательно расскажи, как ты останавливаешь сервис. Сначала закрываешь листенер для новых сообщений (`consumer.Close()`), потом дожидаешься, пока текущие горутины закончат работу (через `sync.WaitGroup`), и только потом выключаешься. Это гарантирует, что мы не потеряем события.

---

### 6. Пример архитектуры для задачи (Чтобы блеснуть)

Представь: система доставки еды.

1.  Сервис **Orders** создает заказ и публикует событие `OrderPlaced` в Kafka (партиция по `user_id`).
2.  Сервис **Payments** читает это, списывает деньги, публикует `PaymentSuccess` или `PaymentFailed`.
3.  Сервис **Notification** подписан на оба эти топика и отправляет пользователю письмо/пуш.

В Go мы бы разделили каждый сервис как отдельный бинарник, общающийся через общий кластер Kafka.

## Расскажи про разницу  между Event Sourcing и EDA

Отличный вопрос! Это **«ловушка»** для джуниоров. На собеседовании 70% кандидатов путают эти понятия или считают, что Event Sourcing — это просто «EDA с хранением событий».

Спойлер: **Event Sourcing — это способ хранения данных (Storage Pattern), а EDA — способ взаимодействия (Communication Pattern)**. Они могут работать вместе, но решают разные задачи.

Вот как нужно разложить ответ, чтобы сеньор закивал головой.

---

### 1. Event-Driven Architecture (EDA) — про **взаимодействие**

- **Суть:** Это **сетевой/интеграционный** паттерн. Сервисы общаются через брокер, не зная друг о друге.
- **Хранилище:** Сервис при этом может хранить данные как угодно — в PostgreSQL, MongoDB, или вообще в памяти. Событие отправляется наружу **после** того, как транзакция с БД уже подтверждена (или до, если мы используем паттерн Transactional Outbox).
- **Жизненный цикл события:** Событие попало в брокер, его обработали, и **событие удаляется** (или истекает по TTL). История не хранится вечно.
- **Цель:** Слабая связанность, асинхронность, масштабируемость.

---

### 2. Event Sourcing (ES) — про **хранение состояния**

- **Суть:** Это **паттерн работы с базой данных**. Вместо того чтобы хранить **текущее состояние** сущности (например, `balance = 100`), мы храним **все события**, которые привели к этому состоянию (события — это **источник истины**, Source of Truth).
- **Хранилище:** БД (Event Store) — это не брокер, это долговременное хранилище (например, PostgreSQL с таблицей `events`, или специализированные EventStoreDB, Axon). События **никогда не удаляются** (append-only).
- **Текущее состояние:** Чтобы получить баланс сейчас, мы берем все события по `user_id` и применяем их по порядку (это называется **State Rebuilding**). Для ускорения используют **Snapshot'ы** (снимки состояния).
- **Цель:** Полный аудит, возможность «откатить» состояние в любой момент времени (Time Travel), воспроизвести ошибку в production, строгая согласованность внутри одного агрегата.

---

### 3. Ключевая разница (Таблица для запоминания)

| Характеристика | EDA (Event-Driven) | Event Sourcing |
| :--- | :--- | :--- |
| **Что это?** | Способ общения сервисов | Способ хранения данных |
| **Где живут события?** | В брокере (Kafka, RabbitMQ) — **временное** хранилище | В Event Store (БД) — **вечное** хранилище (append-only) |
| **Откуда берется текущее состояние?** | Из обычной БД (обновляется перезаписью) | Пересчитывается из всех прошлых событий |
| **Обновление данных** | `UPDATE users SET balance=100` | `INSERT INTO events (type='MoneyAdded', amount=10)` |
| **Консистентность** | Как правило, **Eventual** (между сервисами) | **Strong** (внутри одного агрегата, т.к. мы читаем события перед записью) |

---

### 4. Самый важный нюанс (Главная путаница)

Многие думают: *«Если я использую Kafka, значит я использую Event Sourcing»* — **НЕТ**.

- В Kafka события живут ограниченное время (retention: 7 дней или 1 ГБ). Это **временной буфер обмена**.
- В Event Sourcing события живут вечно (пока существует система).

Но! Их часто **комбинируют**:
1. В Event Store пишется событие `OrderPlaced`.
2. Специальный компонент (Reactor/Projector) читает это событие из Event Store и **публикует его в Kafka** (EDA), чтобы другие микросервисы узнали о новом заказе.
3. Другие сервисы (например, Payment) получают событие через Kafka, обрабатывают его и **пишут СВОИ** события в СВОЙ Event Store.

---

### 5. Когда что выбирать? (Показать инженерное мышление)

**Выбираем EDA (без ES):**
- Нам нужна обычная CRUD-магия.
- Данные можно перезаписывать (например, профиль пользователя).
- Нам плевать на историю изменений.
- *Пример:* Сервис уведомлений — получил событие, отправил письмо, забыл.

**Выбираем Event Sourcing (строго внутри одного сервиса):**
- **Финансы/Бухгалтерия** — каждую копейку нужно отследить и нельзя терять историю.
- **Системы бронирования** (билеты, отели) — нужна строгая согласованность, чтобы два человека не купили одно место.
- **Аудит и Compliance** — нужен "журнал" всех действий за 10 лет.

---

### 6. Особенности реализации в Go (Если ты смелый)

Если на собеседовании спросят "А как бы ты это делал на Go?":

**Для EDA:**
Используем `sarama` или `nats.go`. Публикуем событие **после** коммита транзакции в БД (чтобы не было ситуации "событие ушло, а данные не сохранились").

**Для Event Sourcing:**
- В Go нет встроенных Event Store, обычно используют `PostgreSQL` как хранилище событий (таблица с полями: `aggregate_id`, `version`, `event_type`, `payload (JSONB)`, `created_at`).
- При сохранении нового события обязательно проверяем **версию агрегата** (Optimistic Locking):
```go
// Перед вставкой проверяем, что версия текущая
res, err := db.Exec(`
    INSERT INTO events (aggregate_id, version, payload) 
    SELECT $1, $2, $3 
    WHERE NOT EXISTS (
        SELECT 1 FROM events WHERE aggregate_id=$1 AND version=$2
    )
`, aggID, nextVersion, payload)
// Если affected rows == 0 — значит кто-то нас опередил (конфликт), откатываем транзакцию
```
- **Snapshot'ы:** Когда событий становится > 1000, мы периодически сохраняем текущее состояние в отдельную таблицу `snapshots`, чтобы не пересчитывать все с нуля при каждом запросе.

---

### 7. Итог для интервьюера (Резюмируй так)

> «EDA отвечает на вопрос **"Как сервисы узнают о действиях друг друга?"** — через брокер.
> Event Sourcing отвечает на вопрос **"Как сервис помнит, что с ним происходило?"** — храня события в БД без удаления.
> Они идеально работают в тандеме: ES обеспечивает надежность и аудит внутри сервиса, а EDA — доставляет эти события наружу. Но использовать ES без острой необходимости — это усложнить себе жизнь в 10 раз (CQRS, сложные миграции, работа с устаревшими версиями событий). Поэтому я бы предложил EDA как базовый стандарт, а Event Sourcing — только для критически важных финансовых агрегатов».

## Теперь про CQRS

Отлично! Теперь мы подошли к **«святому граалю»** архитектурных собеседований. CQRS — это та тема, где джуниоры цитируют Википедию, а сеньоры говорят: *«Это дорогой инструмент для специфических задач, и я не буду использовать его для CRUD-а».*

Готовься: сейчас мы разберем это так, что интервьюер поймет — ты **делал это руками** и обжигался.

---

### 1. Определение (Суть за 10 секунд)

**CQRS** (Command Query Responsibility Segregation) — это паттерн, который предписывает **разделить модели данных для чтения (Query) и записи (Command)**.

В классическом CRUD-подходе мы используем **одну и ту же модель** (и таблицу в БД, и структуру в Go) и для вставки, и для выборки. CQRS говорит: *«Это неправильно, если система сложная»*.

---

### 2. Аналогия для понимания (Скажи это на собеседовании)

Представь библиотеку:

- **Command (Запись):** Библиотекарь строго заполняет карточку учета, проверяет уникальность читательского билета, соблюдает все правила. Это **медленно**, но **гарантирует консистентность**.
- **Query (Чтение):** Читатель заходит в каталог и ищет книги по авторам, жанрам и году. Ему плевать на правила записи, ему нужна **удобная выборка** и **скорость**.

В CRUD мы бы пытались читать прямо из той же карточки, где библиотекарь заполняет данные, и постоянно ловили бы блокировки. CQRS говорит: «Давайте сделаем отдельный читальный зал с удобными каталогами, куда мы будем приносить копии карточек».

---

### 3. Архитектурная схема (Обязательно нарисуй в голове)

В CQRS появляются два четких пути:

1.  **Command Side (Write Side):**
    - Принимает запрос на изменение (например, `CreateOrderCommand`).
    - Проверяет бизнес-правила (валидация, инварианты).
    - Сохраняет данные в **Primary (Write) БД**. Часто — в нормализованном виде.
    - **Никаких `SELECT *` для отображения списков здесь нет!**

2.  **Query Side (Read Side):**
    - Принимает запрос на получение данных (например, `GetOrderListQuery`).
    - Выполняет сложные, нестандартные, денормализованные запросы.
    - Читает из **Read (Replica) БД**, которая оптимизирована под запросы (индексы, материализованные представления, документные хранилища).

3.  **Синхронизация (Самое сложное):** Данные из Write БД попадают в Read БД **асинхронно**. Как правило, через **Event Sourcing** или просто через публикацию событий и их проекцию.

---

### 4. CQRS vs CRUD (Ключевые отличия)

| CRUD | CQRS |
| :--- | :--- |
| Одна модель для чтения и записи | Две модели (иногда больше для разных UI) |
| Обновление через `UPDATE` перезаписью | Обновление через **события** (или явные команды) |
| Данные консистентны моментально (ACID) | Данные консистентны **в конечном счете** (Eventual Consistency) |
| Просто, дешево, предсказуемо | Дорого, сложно, но гибко |
| `type Order struct { ID, Price, Status }` используется везде | `WriteOrder{ID, Price, Items}` и `ReadOrder{ID, Total, CustomerName, ItemCount}` — разные структуры |

---

### 5. Почему CQRS нужен? (Когда применять)

Никогда не используй CQRS "на всякий случай". Вот симптомы, что он нужен:

- **Read/Write нагрузки отличаются в разы:** Например, 10 000 запросов на чтение в секунду и 10 запросов на запись. Ты не можешь строить тяжелые индексы для чтения, потому что они тормозят запись.
- **Сложные запросы:** Тебе нужно делать JOIN 10 таблиц с аггрегациями, чтобы показать "Дашборд аналитика". Запись же должна проходить по строгим правилам (Unique, Foreign Keys).
- **Разные команды:** У тебя сложная бизнес-логика (Saga), где одно действие триггерит каскад изменений.
- **Разные команды для разных клиентов:** Мобильное приложение хочет сжатую модель, Веб-админка — расширенную, API для партнеров — свою.

---

### 6. А теперь — **Подводные камни** (За это дают +100 к карме на собеседовании)

1.  **Дублирование кода:** У тебя будет две структуры для одной сущности. Придется писать мапперы (конвертеры). Это утомляет.
2.  **Eventual Consistency:** Пользователь создал заказ, нажал F5, а заказа еще нет в списке. Через 500 мс он появится. **Это нужно объяснять бизнесу!**
3.  **Синхронизация — боль:** Если проектор (сервис, который обновляет Read БД) упал, то Read БД устаревает. Нужен мониторинг лагов (лаг в репликации).
4.  **Транзакции:** Нельзя сделать атомарное обновление в двух разных БД в рамках одной транзакции. Это одна из причин, почему CQRS часто комбинируют с **Event Sourcing** — там транзакция идет внутри одного Event Store, а проекции обновляются асинхронно.

---

### 7. CQRS + Event Sourcing + EDA (Святая троица)

На собеседовании покажи, что ты понимаешь, как они стыкуются:

1.  **EDA** — это то, как **команды и события** путешествуют между сервисами (через Kafka).
2.  **Event Sourcing** — это то, как мы **храним** изменения на Command Side (не `UPDATE`, а `INSERT` событий).
3.  **CQRS** — это то, как мы **строим модели** для чтения. Проектор слушает события из Event Store (или брокера) и заполняет Read БД.

**Архитектура в Go:**
- Command Handler принимает gRPC/HTTP, проверяет, сохраняет событие в PostgreSQL (Event Store).
- После сохранения публикует событие в **NATS/Kafka**.
- Отдельный **Projector** (на Go) читает из NATS, строит денормализованный документ и сохраняет его в **MongoDB или Elasticsearch**.
- Query Handler читает из MongoDB и отдает JSON с огромной скоростью.

---

### 8. Реализация в Go (Код для сеньора)

Даже если не попросят написать код, скажи алгоритм. Вот как это выглядит:

**Структуры (разделяем):**
```go
// Для записи (Command) - строгая, содержит бизнес-логику
type WriteOrder struct {
    ID     string
    UserID string
    Items  []WriteItem
    Total  decimal.Decimal
}

// Для чтения (Query) - денормализованная, готовая к отображению
type ReadOrder struct {
    OrderID      string    `json:"id"`
    CustomerName string    `json:"customer"` // Денормализовано из UserService
    TotalPrice   float64   `json:"total"`
    ItemsCount   int       `json:"count"`
    CreatedAt    time.Time `json:"created"`
}
```

**Command Handler (пишем):**
```go
func (h *CommandHandler) CreateOrder(ctx context.Context, cmd CreateOrderCmd) error {
    // 1. Бизнес-логика (валидация)
    if cmd.Total.IsNegative() { return errors.New("invalid total") }

    // 2. Сохраняем событие в Event Store (если используем ES)
    event := OrderCreatedEvent{OrderID: cmd.ID, UserID: cmd.UserID, Total: cmd.Total}
    if err := h.eventStore.Append(ctx, event); err != nil {
        return err
    }

    // 3. Публикуем событие в Kafka для проектора (EDA)
    return h.producer.Publish(ctx, "orders", event)
}
```

**Projector (обновляем Read модель):**
```go
func (p *Projector) HandleEvent(ctx context.Context, event OrderCreatedEvent) error {
    // 1. Делаем запрос в UserService (или берем из кэша), чтобы получить имя
    user, _ := p.userClient.GetUser(ctx, event.UserID)

    // 2. Сохраняем денормализованную запись в Read БД (Mongo/Postgres)
    readOrder := ReadOrder{
        OrderID:      event.OrderID,
        CustomerName: user.Name,
        TotalPrice:   event.Total.InexactFloat64(),
        ItemsCount:   len(event.Items),
        CreatedAt:    time.Now(),
    }
    return p.readDB.Save(ctx, readOrder) // Upsert
}
```

### 9. Итог для интервьюера

> «CQRS — это про **разделение ответственности**, а не про "крутую архитектуру". Я рассматриваю его как **компромисс**: мы жертвуем простотой (дублирование моделей, асинхронность) ради производительности и гибкости запросов.
>
> В Go это реализуется естественно, потому что у нас строгая типизация, и мы легко разделяем пакеты `internal/write` и `internal/read`. Но внедрять я его буду только в том случае, если мы видим реальную проблему с нагрузкой на БД. Если же проект — это админка на 100 пользователей, я выберу стандартный CRUD с PostgreSQL и хорошо настроенными индексами.
>
> Самое главное в CQRS — **не пытаться синхронизировать Read и Write синхронно** через двухфазный коммит. Нужно принять Eventual Consistency и построить здоровый мониторинг лагов проектора».
